# Foundation

Foundation mono-repo for Sgt Flame's Project Veritas, "The Right Answer".

## Architecture

See [ARCHITECTURE.md](ARCHITECTURE.md) for the tech stack. Use `yarn`, never `npm`, for the frontend.

### Services, handlers and DTOs

Every backend service follows the same service → handler → DTO layout, with a matching frontend client. A feature `<f>` holds one or more services `<s>`; its main service is named after the feature (`<s>` = `<f>`). `kb` (Knowledge Base) is the reference, with two services: `kbservice` and `volumeservice`. For a service `<s>` with an operation `<Op>`:

**Service** - `backend/features/<f>/services/<s>service/`
- `Service.go` - the `Service` interface plus each operation's `<Op>Args` (embedding `features.ServiceArgs`), `<Op>Response` (with `Common features.ServiceResponse`) and, for async operations, `<Op>Request` holding the response channel. No implementation lives here. `ServiceArgs` holds `Ctx` (the request's context: cancellation, trace and log context; read it with `args.Context()`), `Principal` and `Meta` (`features.Meta`: what the work is for, such as `Feature`, `Level`, the conversation, and the Cognition `RunID`/`NodeID`, so usage can be attributed; set what you know with `args.Meta.WithFeature("embed-index")`); operations never add their own `Ctx` or tenant fields, and a service calling another passes its `ServiceArgs` on (`embedservice.EmbedArgs{ServiceArgs: args.ServiceArgs, ...}`). Code below the service layer that only gets a context (AI providers) gets `args.CallContext()`, from which `features.CallFrom(ctx)` reads the principal and Meta back.
- `impl/factory.go` - `CreateService(opts ...Option) <s>service.Service` returns a singleton built on first call. Configuration has defaults and is overridden only through `Option` functions named `With<Setting>` (e.g. `WithRoot`); options passed after the first call are ignored.
- `impl/<Op>.go` - one file per operation; an operation only Go code calls (such as `collabservice.EditFile`, which the `kb.edit` tool calls) says so on the interface and has no handler, DTO or client method. Success is `Common: features.OK()`; failure is `Common: *args.Fail(status, err)` with a `net/http` status and an error from the logging builder (see *Errors and logging*). A new operation starts with `authz.Check` (see *Access and tenancy*).

- Other files in `<s>service/` hold shared types and helpers other services may use, such as `kbservice/VolumePath.go` and `volumeservice/Marker.go`.

**Handlers** - `backend/features/<f>/rest/<s>handlers/`
- `register.go` - `Register(router gin.IRouter, service <s>service.Service)` stores the service on the handler struct and maps routes under `/<f>` (a secondary service under `/<f>/<resource>`, e.g. `/kb/volumes`); `router` is the `/api/v1` group, so routes are served at `/api/v1/<f>/...`.
- `<Op>.go` - one gin handler per operation: `args, ok := rest.Bind(c, &req)` (it answers 400 itself, so return when `!ok`), call the service with `req.ToArgs(args)`, and respond with `Common.Code` as the HTTP status and `<Op>ResponseFrom(resp)` as the body. An operation with no body (`GET`) passes `rest.Args(c)` instead. Handlers only translate; logic belongs in the service.

**DTOs** - `backend/features/<f>/rest/<s>dto/`
- `<Op>Request.go` - the JSON request, with `ToArgs(args features.ServiceArgs) <s>service.<Op>Args` setting `ServiceArgs: args`. Requests never carry a tenant or user: those come from the principal.
- `<Op>Response.go` - the JSON response, embedding `rest.Status` (`message` and `errorCode`, both empty on success), with `<Op>ResponseFrom(<s>service.<Op>Response) <Op>Response` setting `Status: rest.StatusFrom(resp.Common)`. The code travels as the HTTP status, not in the body, and the trace is never in the body.
- Types shared between DTOs (e.g. `VolumePath.go`, `FolderEntry.go`) get their own file with their own conversion. A DTO package may reuse another's shared types (`volumedto` uses `kbdto.VolumePath`).
- JSON fields are camelCase. Every `uint64` (IDs, TSIDs) is tagged `,string` so it travels as a JSON string. New IDs come from `features.NewTSID()`.

**Wiring** - `backend/cli/cmd/serve.go` sets up logging (`--log-format text|json`, `--log-level` for stderr, `--vlogs-url` for storage), listens at once behind a `secrets.Gate` that serves only the bootstrap routes (503 `server_starting`, or `server_sealed`, for every other API route) and, with `--vault-addr`, waits to be unsealed (see *Secrets* below), opens and migrates the application and tenant databases, creates each service with its `impl.CreateService(...)` (imported as `<s>impl`), then each handler, and calls `Register(api, service)`; once it is done, `gate.Open(router)` serves the router. The router is `gin.New()` with `rest.Middleware(rest.WithAuthenticate(...))` (trace, principal and one log record per request, in place of gin's logger) and `gin.Recovery()`; its groups are `public` (`/api/v1`, only the identity routes), `api` (`public` with `rest.RequireUser()`, where a new handler goes) and `volumes` (`api` with `kbhandlers.InTenant()`, for kb, collab and index). Services that react to each other are joined by in-process buses (`features/events.Bus[T]`, synchronous: subscribers must not block), passed in with `With<Bus>` options, e.g. `volumeservice.FileEvents`.

**Errors and logging** - `features/logging` (see `documentation/Logging.md`) is the one way to log and make errors; never `slog.*` or `fmt.Errorf` in a service. A `logging.Builder` mirrors the frontend `log` and `samber/oops`: `log.Code("volume_not_found").With("volumeId", id).Errorf("volume %q does not exist", rel)` makes an oops error, and `log.Info(ctx, ...)`/`log.Error(ctx, err, ...)` log a record carrying the request's trace, user and tenant from `ctx`. Each impl package declares its builder as `var log = ...` (`volumeservice.Log.Tags("volume")`, `providers.Log.Tags("chat")`, `logging.In("index")`). `args.Fail(status, err)` turns an error into `*ServiceResponse` and logs it once (5xx at error, 4xx at debug), so callers never log a failure again; `Message` is the error's `Public` text, else a 4xx's own text (so 4xx errors name nothing private, e.g. folders relative to the root) or a 5xx's status text; `ErrorCode` is the oops code. Low-level helpers (`lancestore`, `VolumePath`, `db`) may return plain errors; the service wraps them with `log.Wrap(err)`. Every request has a trace: the browser sends `X-Trace-Id`, `rest.Middleware` accepts or makes one and echoes it; records and errors in the request share it.

**Access and tenancy** - Every request runs as a `features.Principal` (`{Kind, UserID, TenantID}`), set by `rest.Middleware(rest.WithAuthenticate(auth.Authenticate))` from the `foundation_access` cookie (`identity.Authenticator`, see *Identity* below). While no user exists (single-user mode) it is `features.LocalPrincipal()` (reserved IDs: tenant 1, user 1, who holds *Super Administrator*); afterwards a request without a valid session is `features.AnonymousPrincipal()`, and `rest.RequireUser()` (on every route group except `/identity`) refuses it with 401 `session_expired` or `unauthenticated`. Background work uses `features.BackgroundArgs(ctx)` (a service principal). Every new operation calls `authz.Check(args.Context(), args.Principal, "<type>.<action>", resource).Err(action, resource)` first and fails with `authz.Status` (403); the action must be declared (see *Roles* below) or it is denied. Resource paths are `app`, `tenant:<id>`, and paths under a tenant built with `authz.Tenant(p)` and `authz.Resource(kind, id)` (`tenant:1/volume:42`, `tenant:1/user:2/chronicles`); a user's own scope is `user:<id>/…`. Volumes, their index and collaboration belong to the default tenant until each tenant has its own knowledge base root: `kbhandlers.InTenant()` guards `/kb` and `/index` (403 `volumes_unavailable`), the `library` source and kb tools check `kbservice.InTenant`. Within the tenant, kb operations check `volume.read|write` on the Volume holding the folder, else `kb.read|write` (`volumeservice.Check`, `volumeservice.Resource`), and the `library` source drops chunks of Volumes the caller may not read. **Roles** (`features/authz`, see `documentation/RBAC.md` › *Built in slice 11*): a feature declares its resource types on `authz.ResourceTypes` (`authz.resourceType`) from a `ContributeAccess(reg)` that `serve.go` calls (`identity`, `config`, `logs`, `usage`, `conversation`, `chronicle`, `retrieval`, `cognition`, `kbservice`; `authz.Contribute` adds `role`, `grant`, `secret`, `extensions`). Each `authz.Action` has a `Class` (`read`, `write`, `create`, `delete`, `share`, `moderate`, `execute`, `admin`, or `self`: no grant needed) and `On` (`app` or `tenant`, the default): pick these with care, since the built-in roles (reserved IDs 1-9: *Super Administrator*, *Tenant Administrator*, *Application Administrator*, *Global Moderator* on `app`; *Owner*, *Administrator*, *Moderator*, *Editor*, *Viewer* in a tenant) take actions by class. A type with `Owned` is the principal's when the path names `user:<their id>`. `serve.go` installs `authz.NewPolicy(appDB, registry)` with `authz.Install` after `identity.MigrateRoles`; `Check` then allows a user when a `RoleGrant` on the path or an ancestor holds the action (allow-only, with optional expiry), and before a policy is installed (other features' tests) allows everyone but anonymous principals. Grants, `CustomRole`s (per tenant) and `AccessAudit` live in the application database; change them through `Policy.Grant`/`Revoke`/`RevokeUnder` (inside a transaction, then `Changed()`), and in identity through `identity.Grant`/`RevokeUnder`/`Changed`. Granting needs `grant.write` and every permission of the role (`Policy.MayGrant`). New members get *Editor* (`identity.DefaultMemberRole`), a tenant's creator *Owner*, and leaving a tenant revokes its grants. `authzservice` (`/authz`: `GET me|resource-types|roles`, `POST roles/save|roles/delete|grants|grant|revoke|explain`) serves the Role Editor, the Share dialog and the browser's `useCan`. Every new tenant-owned table embeds `db.Tenanted` after `db.Model`, and a user-owned one `db.Owned` too, filled from the principal (`db.TenantOf(p)`, `db.OwnedBy(p)`) and queried with `.Scopes(db.InTenant(p.TenantID))`.

**Extension points** - `features/extensions` (see `documentation/Contributors.md`): the owning feature declares `var X = extensions.NewPoint[T](id, description)`, where a contribution `T` embeds `extensions.Descriptor{ID, Order, Source}`; contributors call `X.Register(reg, c)` from a `Contribute(reg *extensions.Registry)` function that `serve.go` calls explicitly (no `init()` side effects), and readers call `X.All(reg)`. `serve.go` declares each point with `registry.Declare(...)`. The backend points are `config.Sections` (`config.section`, `features/config`), `conversation.ContextProviders` (`chat.contextProvider`, `features/conversation`), `conversation.RoundFollowers` (`chat.roundFollower`: work after a successful reply, reported as a `followed` event), `retrieval.Sources` (`retrieval.source`, `features/retrieval`), Cognition's `cognition.Nodes` (`cognition.node`), `cognition.Graphs` (`cognition.graph`, built-in graphs) and `cognition.Types` (`cognition.type`, data types and their colours), `tools.Tools` (`tools.tool`, functions the model may call), and `authz.ResourceTypes` (`authz.resourceType`, see *Roles* above). `aisettings.Contribute` (`features/ai/settings`) registers `ai.providers`, `ai.models`, `ai.chat.levels` and `ai.chat.stages` (the level of each internal call: Chronicle's `match` and `memory`); `logssettings.Contribute` registers `logging`; `usagesettings.Contribute` registers `usage.capture`; `retrievalsettings.Contribute` registers `retrieval`, `retrieval.feedback` and `chat.context.presets`; `indexsource.Contribute` (`features/index/source`) registers the `library` retrieval source over the LanceDB store and `chroniclesource.Contribute` (`features/chronicle/source`) the `chronicle` source over the entries table (so `serve.go` opens both LanceDB tables before building the registry); `chroniclecontext.Contribute` (`features/chronicle/context`) registers the `chronicle` context provider (stage 1) and round follower (the memory update), taking a function that returns their dependencies; `retrievalcontext.Contribute` (`features/retrieval/context`) registers the `rag` context provider, taking a function that returns the retrieval service, which is created later (configuration needs the finished registry first: break such cycles with a late-bound function, not by reordering); `workbenchcontext.Contribute` (`features/workbench/context`) registers the `workbench` context provider; `conversationsettings.Contribute` registers `chat` plus a `chat.context.defaults.<id>` section per context provider, so it runs after the providers; `cognitionsettings.Contribute` registers `cognition`; `cognitionnodes.Contribute` (`features/cognition/nodes`) the Branch and Return nodes and the core data types; `conversationnodes.Contribute` (`features/conversation/nodes`) Chat's events (`event.userMessage`, `event.reply`) and types; and `chroniclenodes.Contribute` (`features/chronicle/nodes`) Chronicle's nodes and the built-in Personal graph, taking a function that returns the step functions. Tools: `toolssettings.Contribute` registers `tools`; `toolsbuiltin.Contribute` (`features/tools/builtin`) `time.now`; `kbtools.Contribute` (`features/kb/tools`) and `chronicletools.Contribute` (`features/chronicle/tools`) the kb and Chronicle tools, each taking a function that returns their services; `toolscontext.Contribute` (`features/tools/context`) the `tools` context provider, which gathers nothing but whose `enabled` setting is a conversation's Tools switch (so it runs before `conversationsettings.Contribute`); and `toolsnodes.Contribute` (`features/tools/nodes`) the `Agent` node (`llm.agent`). A contribution that needs a browser control and server logic uses the same id on both sides (`chat.contextSettings` `workbench` ↔ `chat.contextProvider` `workbench`, `rag` ↔ `rag`, `chronicle` ↔ `chronicle`). `extensionsservice` (`GET /api/v1/extensions/points`) describes the registry for DevTools.

**Configuration** - `features/config` (see `documentation/Configuration.md` › *Built in slice 2*). A feature declares a `config.Section` (`Schema` and `Defaults` as raw JSON in the schema subset of `config/Schema.go`, optional `Check` and `Migrate`) and registers it from its `Contribute`; a section's value is always a JSON object, and paths are dotted with array items by index (`levels.0.modelRef`). Values resolve defaults → server → env → `app` → `tenant` → `user`, except that a flag or env value (`configimpl.WithEnv(section, path, value)`) wins over everything for `secret` fields. Services read settings with `config.Read[T](configService, args, sectionID)` (cached; secrets in plain text, Go only) and react to `config.Changes` (`config.Changed{Section, Scope}`). Never hand a secret to a client: `configservice` returns `{set, hint}` in its place (`{set}` with Vault). Secrets are kept through a `config.SecretStore` (`configimpl.WithSecrets`), which leaves a placeholder in the row: `config.CipherStore` seals them with AES-GCM in the row (`{"$secret": …}`, key `$FOUNDATION_SECRET_KEY` or `<data-dir>/secret.key`), and `vaultstore` (with `--vault-addr`) keeps them in Vault at `config/<scope>/<section>/<path>` (`{"$vault": {"version": n}}`); a save writes only the secrets it changed. `configimpl.WithServerSecret` adds the server's own secret from Vault's bootstrap bundle under every scope (source `server`). Plain settings need `config.write`; secrets need `secret.write` on `app` at the app scope (an *Application Administrator*) and `config.writeSecrets` elsewhere, and Settings lets a user edit only the fields they may write. REST: `GET /config/sections`, `POST /config/get|set|reset` (`set` takes a JSON merge patch and the view's `revision`: 409 `config_conflict` when stale, 400 `invalid_settings` with `errors: [{path, message}]`), and `GET /config/events` (SSE). Requests name a scope kind (`app`, `tenant`, `user`), never IDs.

**Usage** - `features/usage` (see `documentation/Usage.md` › *Built in slice 2*): `serve.go` wraps the provider with `usage.ChatProvider`/`usage.EmbedProvider` before `WithProvider`, so every provider call becomes a `usage.Record` (tenant, user, `Meta`, tokens, latency, status), priced from `ai.models` when queued (`aisettings.Pricing.CostMicros`, micro-units) and written in batches by `usage.Recorder` (closed on shutdown); records are published on `usage.Events`. `usageservice.Records` (`POST /usage/records`) pages through them; DevTools' Usage tab shows them. `usageservice.Summary` (`POST /usage/summary`) sums them for the Dashboard: totals plus a row per `bucket` (`hour`, `day`, `month`, shifted by `tzOffsetMinutes`) and `groupBy` (`feature`, `model`, `level`, `conversation`; allow-listed, never interpolated), `limit` keeping the costliest groups; costs are summed in micros whatever the currency (all USD for now). Records never hold prompt or reply text: with the `usage.capture` setting on (off by default), a chat call's system prompt, messages and reply go to `usage.Capture` (`usage_captures`, keyed by `RecordID`; the record gets `Captured`), purged after `retentionHours` (24) by the recorder, and read with `usageservice.Capture` (`POST /usage/capture`, 404 `capture_not_found` once expired). Logs never carry prompts or replies.

**Logs** - `features/logs` (see `documentation/Logging.md` › *Built in slice 3*). Records always go to stderr, and also to VictoriaLogs through `logging.Victoria` (a sink passed to `logging.Setup`: a bounded queue posted in batches to `/insert/jsonline` with `Content-Type: application/stream+json`, never blocking a request; it reports its own failures on stderr, never through slog). Where and from what level is the `logging` section (Settings › System › Logging, off by default; `--vlogs-url` or `$FOUNDATION_VLOGS_URL` wins), applied live by `serve.go`. `logsservice` (`/logs`: `GET status`, `POST query|hits|fields/names|fields/values|streams|tail|ingest`) is a thin wrapper over VictoriaLogs' HTTP API: it scopes to the tenant with `extra_filters` unless `logs.readAll` allows, bounds rows (500, at most 5000) and ranges (31 days), turns a LogsQL parse error into 400 `bad_query` with `queryError{message, offset}`, relays `tail` as SSE, and stores browser records from `ingest` with `source=browser` and the principal's user and tenant. `backend/scripts/victorialogs.sh` runs VictoriaLogs (pinned v1.53.0) on `:9428` for development.

**Building** - LanceDB needs CGO and a native library, so build, test and vet through `backend/scripts/build.sh` (`-o <out>`, `--test [pkgs]`, `--vet [pkgs]`), never bare `go build`; where memory is short (the 7 GB codespace) the linker is killed while linking `out/cli` (and test binaries, while the vite dev server and `serve` run), and `GOGC=25 GOFLAGS=-ldflags=-s backend/scripts/build.sh` (also with `--test`) links without debug symbols; packages that do not import LanceDB still `go test` normally. `scripts/serve.sh [serve flags]` sources `scripts/setEnv.sh` (gitignored, made from `setEnv.example.sh`: `GEMINI_API_KEY` and the other env vars), builds `out/cli`, runs `serve`, and rebuilds and restarts it on every Go change (a failed build keeps the old server). `go.mod` pins lancedb-go to a `main` commit for full-text search, so the first build compiles its library from Rust (see `documentation/AIChatEmbed.md`).

**Database** - `backend/features/db`: SQLite through GORM (`db.Open`), migrated by `serve` at startup (`db.Migrate` with each feature's models, e.g. `config.Models()`, `usage.Models()`). There are two: the **application database** (`--app-db`, `<data-dir>/app.db`: what spans tenants, `identity.Models()`, `logs.Models()`, `authz.Models()` and `secrets.Models()`) and the **tenant database** (`--db`, `<data-dir>/foundation.db`: every other table, filtered by `TenantID`); a new table goes in the tenant database unless it spans tenants. LanceDB is one directory per tenant, `db.TenantDir(<data-dir>/lancedb, tenantID)` (tables from before tenants are moved into tenant 1's once by `db.MoveToTenantDir`); Chronicle entries use `entrystore.Tenants`, and the index's chunks are tenant 1's (`lancedb/1`). Never run two queries on one GORM chain (`q := s.db.Where(...)`, then `q.First(&a)` and `q.Find(&b)`): the second inherits the first's table; build a new chain per query, e.g. with a small function as `cognitionservice.GetTrace` does. Every table embeds `db.Model`: its primary key is a TSID assigned on create, never an auto-increment number. Tenant- and user-owned tables also embed `db.Tenanted`/`db.Owned` (see *Access and tenancy*).

**Frontend client** - `frontend/common/src/services/<Service>.ts`, one per backend service (`KnowledgeBase.ts` for `kbservice`, `Volume.ts` for `volumeservice`)
- Declares its own DTO interfaces mirroring the backend `<s>dto` JSON exactly, importing shared ones from the client that declares them (`Volume.ts` imports `VolumePath` from `KnowledgeBase.ts`). Response interfaces extend `ResponseStatus` (`message?`, `errorCode?`) from `http/client.ts`. Every `uint64` is a `string` in TypeScript, since a JavaScript number cannot hold every uint64; never convert IDs to `number`.
- Exports one object named after the service with one method per handler (`KnowledgeBase.openVolume(request)`), returning a `Promise` of the response DTO and throwing `ServiceError` (`status`, `message`, `errorCode`, and the request's `trace`) on a non-2xx status.
- Requests go through the shared axios instance `http` from `src/services/http/client.ts` (e.g. `http.post<Resp>('/kb/volumes/open', request)`), whose baseURL is `API_BASE` (`VITE_API_BASE`, default `/api/v1`). `Retrieval.ts` is the retrieval client, `Cognition.ts` the Cognition client. In dev, the `foundation()` Vite plugin (`frontend/common/vite.ts`) proxies `/api/v1/<f>` to the backend on `localhost:8080`; a new feature adds its route to `routes` there, while a new service in an existing feature is already covered.
- `http` records every exchange into DevTools' Network tab by default. Opt out per request with `{ capture: false }` in the axios config, or per client with `createHttpClient({ capture: false })`.
- `http` sends a new trace ID (`newTraceId()` from `http/trace.ts`) as `X-Trace-Id` on every request, kept in `config.traceId`; DevTools' http log records carry it as their `trace`.
- Components call these clients; they never `fetch` or use axios on the backend directly. `Chronicle.ts` is the Chronicle client. The clients using `fetch` are `Chat.stream`, `Conversations.send` (with `onFollowed`) and `Logs.tail`, because axios cannot stream Server-Sent Events in the browser; they parse with `http/sse.ts`, set `X-Trace-Id` themselves and, like collab's WebSocket and `Config.events` (an `EventSource`), are logged, not captured. `Logs.ingest` opts out of capture too, and so do `Secrets.put` and `Config.set` with a patch carrying a secret (`{ secret: true }`): no secret value is ever captured. `Secrets.ts` is the secrets client and `Bootstrap.ts` reads the bootstrap state.
- A client may resolve a failure status it expects callers to handle inline: `Config.set` resolves a 400 that carries field `errors` (`validateStatus`), and throws `ServiceError` otherwise. The `Logs` query methods throw `QueryServiceError`, a `ServiceError` with the `queryError` of a 400.

Adding an operation touches all five: service interface + `impl/<Op>.go`, handler `<Op>.go` + route in `register.go`, `<Op>Request.go`/`<Op>Response.go`, and a method + DTOs in the frontend client.

### AI and the index

See `documentation/AIChatEmbed.md`. `ai` has two provider-neutral services, `embedservice` (`/ai/embed`) and `chatservice` (`/ai/chat`, with `/ai/chat/stream` as Server-Sent Events), each taking a `Provider` through `impl.WithProvider`. Providers live in `features/ai/providers/<name>/` and return `providers.Error` so failures carry a status; `gemini` is the only one. Its key is chosen per call (`gemini.WithKeyFor`): the `ai.providers` setting as the call's principal (`features.CallFrom`) sees it, so a user's or tenant's own key is used for their calls, and calls with no principal (indexing) use the default tenant's; `--gemini-api-key` or `$GEMINI_API_KEY` wins over every stored key, and without any key AI calls fail with 503 and the server still runs. The model catalog with pricing is `ai.models` and the chat levels (Fast ⚡ flash-lite, Standard 💡 flash, the default, Deep 🧪 pro) are `ai.chat.levels`. `CompleteArgs.Level` (`level` in the REST requests) makes `chatservice` read the level and the catalog through `config.Read` and fill the model, temperature, max output tokens and thinking budget the caller left unset, and set `Meta.Level` (Gemini 3 models refuse a budget of 0, so the provider sends it as their lowest `thinkingLevel`); the `chat` section's `debug` switch sets `Meta.Debug` on a round's calls, and `chatservice` and the provider then log each call's settings, request shape and the provider's full error at info/warn, never prompts or replies; without a level the provider's default model (`--chat-model`) is used. `chatservice.Usage` counts input (including cached), cached, output and thinking tokens separately. **Tool calling**: `CompleteArgs.Tools` (`ToolSpec{Name, Description, Parameters}`) and `ToolChoice` (`""`, `none`, `required`); the response's `Message.ToolCalls` (`{ID, Name, Args, Signature}`, the signature being Gemini's thought signature, sent back with the call); results go back as a `RoleTool` message with `Results`. Calls are not streamed: they come whole in the response. `index` (`indexservice`, `/index`) keeps volume markdown chunked (by heading, at most 4096 bytes, 512 overlapping), embedded and searchable in LanceDB (`index/store/lancestore`, `<data-dir>/lancedb`): `Find` fuses vector and BM25 rankings by weighted Reciprocal Rank Fusion. Each indexed file has a dotted sidecar `.<name>.md.index.json` (`indexservice.Meta`) with each chunk's hash, offsets, lines and head/tail anchors; unchanged chunks keep their embeddings. `conversation` (`features/conversation`, see `documentation/ChatCompletion.md` › *Built in slice 4*) runs AgentOS › Chat: `Conversation` and `Round` tables (tenanted and owned; queries always filter on the owner), and `conversationservice` under `/conversation` (`POST list|rounds|send`, `GET context-providers`). `Send` stores the round first (status 0, so usage `Meta` carries its `RoundID`), runs the enabled `chat.contextProvider`s concurrently and appends their items after the `chat` section's system prompt as data, sends the window (the last `historyRounds` rounds, 15 by default) as plain messages (reply text only, never tool calls) and passes it to the providers as `GatherArgs.Window`, with `Meta` naming the round, runs `tools.Loop` at the round's level with the server's tools and the browser's declared `clientTools` while the conversation's `tools` setting is on (no tools: one streamed call), and completes the round with every step's tokens and cost summed: 200, 499 when stopped (the partial reply is kept; writes use `context.WithoutCancel`), or the failure's status and message. Its SSE events are `started`, `delta`, `tool` (a `ToolCall` each time its status changes; `awaiting` and `client` wait for `answer`), `done`, `title` (generated after the first round at `chat.titleLevel`, `Feature = chat-title`) and `followed` (what each `chat.roundFollower` did, run after the title on a context the browser cannot cancel); a message refused before its round exists gets a plain JSON error. Rounds copy their tokens and cost, priced like the usage record. A `ContextItem` with a `Segment` is citable: `Send` puts `Pinned` segments first in their provider's order, then the rest by score, keeps a segment found twice once (pinned), numbers them `[1]…[n]` in the prompt in the order they fit, stores them as `retrieval.RoundSegment`s and sends them as a `sources` event before the first `delta` (and again when a tool's result adds segments, numbered after them; one already cited keeps its number); `rounds` also returns each round's `toolCalls`; `rounds` returns each round's `segments` and `feedback`, `POST /conversation/feedback {roundId, feedback}` sets the verdict (`up`, `down`, `ignore` or `""`; 🚫 rounds leave the history), and `list` takes `ids`. `GatherArgs.ContextWindow` is the round's model's window. The Markdown editor's Chat tab is planned in `documentation/plans/ChatCompletion.md`.

**Identity** - `identity` (`features/identity`, see `documentation/MultiTenant.md` › *Built in slice 10*): `Tenant`, `User` (argon2id password, `Disabled`; `SuperAdmin` is not a column but read from the grants with `identity.MarkSuperAdmins`, DTO `superAdmin`), `Membership`, `RefreshToken` (SHA-256 only, rotating `Family`) and `SigningKey` (sealed by `config.Cipher`, whose key is Vault's `server/db-key` with Vault) in the application database. A session is a 15-minute HS256 JWT (`identity.Signer`) in the HTTP-only `foundation_access` cookie (path `/api`) plus a 30-day refresh token in `foundation_refresh` (path `/api/v1/identity`), both `SameSite=Strict`; `identity.Sessions` starts, rotates (a replaced token reused within 30 s only gets an access token; later, its family is revoked), ends and revokes them, and `TenantFor` picks where a session starts. `identityservice` (`/identity`: `GET status`, `POST setup|login|refresh|logout|switch-tenant|account`; the handlers set and clear the cookies, bodies carry only `expiresAt` and `account`), `tenantservice` (`/identity/tenants`: `POST list|create|rename|delete|members|add-member|remove-member`) and `userservice` (`/identity/users`: `POST list|create|update`). `/setup` works only while no user exists and makes tenant 1 and user 1. Anything that changes what a user may do (membership, *Super Administrator*, `Disabled`, a new password) revokes their refresh tokens and raises `PolicyVersion`. Users are disabled, never deleted; the default tenant cannot be deleted; one enabled *Super Administrator* always remains. `identity.MigrateRoles` (at start) turned slice 10's `users.admin` flag into grants once and dropped the column; while no user exists, `identity.Bootstrap` keeps user 1 *Super Administrator* and *Owner* of tenant 1. `features.GlobalTenantID` (2) is reserved for content shared with every tenant: no row, no members. **Full logging for one user**: `logs.UserLogLevel` (application database), `logsservice.SetUserLevel`/`UserLevels`/`Level` (`POST /logs/user-level|user-levels`, `GET /logs/level`), applied by `logging.Victoria.SetUserLevels` (that user's records are stored from their own level).

**Secrets** - `secrets` (`features/secrets`, see `documentation/Secrets.md` › *Built in slice 12*) keeps the server's secrets in HashiCorp Vault. `serve --vault-addr` (default `$FOUNDATION_VAULT_ADDR`; `--vault-mount foundation`, `--vault-role-id`) starts **sealed**: `secrets.Bootstrap` waits until `POST /api/v1/bootstrap/unseal {token, roleId}` brings a response-wrapped, single-use AppRole SecretID (checked with `sys/wrapping/lookup` before it is spent), logs in, and reads the **bootstrap bundle**, every one-value secret under `<mount>/server/` (`server/db-key`, the `config.Cipher` key; `server/gemini-api-key`, the server's key under every stored one), once; then startup continues. `GET /api/v1/bootstrap/status` (no session) gives the state, `sealed`, `starting`, `ready` or `degraded`: any failed Vault request but a missing secret, or a failed renewal of the periodic token, degrades it (`Bootstrap.Lost`) while cached values keep it running, and a renewal or a new unseal restores it. `features/secrets/vault` is a small `net/http` client (no Vault SDK); `vault/vaulttest` is an in-memory Vault for tests. `secretsservice` (`/secrets`: `GET status`, `POST list|put|delete`; `secret.list`/`secret.write` on `app`) lists `server/<name>` secrets and the app scope's secret settings (`config/app/<section>/<path>`, written through `configservice.Set`), never values, and audits each write in `SecretAudit` (application database); `server/db-key` is protected. `cli secrets migrate` moves `$secret` values into Vault and re-seals the signing key with `server/db-key`; `cli secrets rekey` rotates the key. The operator's scripts are `backend/scripts/secrets/` (`vault-dev.sh`, `init.sh`, `set.sh`, `list.sh`, `delete.sh`, `rotate-db-key.sh`, `unseal.sh`, sharing `lib.sh`): `curl` and `jq` with the operator's `VAULT_ADDR`/`VAULT_TOKEN`, values from stdin and never on a command line.

`tools` (`features/tools`, see `documentation/Tools.md` › *Built in slice 8*) is function calling. A `tools.Tool` is a struct (`Descriptor` ID = the dotted name, sent to the model with `.` as `_`; `Title`, `Description`, `Input` JSON Schema, `Effect` `none|read|write|external|ui`, `Location` `server|client`, `Wait`, `Run(tools.Call) (tools.Result, error)`); a tool reads its arguments with `tools.Decode[T](call)` after the loop's `CheckArgs`, and returns `Result{Content map, Summary markdown, Segments}`, where segments become citations; an error's text goes to the model and the user, so it names nothing private (pass a service's `Common.Message`). `tools.Loop{DB, Chat}.Run(RunArgs)` is the one tool loop: it streams each step, runs calls (consecutive quiet ones in parallel), asks a `Gate` before `write`/`external` calls unless `Allowed`, has the gate run client tools, stores a `ToolCall` record per call (round or run and node, status, approval, result cut to the `tools` section's `maxResultKB`), and after `maxSteps` makes the model answer. Without a gate (the Agent node) writes are denied and there are no client tools. Chat's gate is in `conversationservice` (`impl/tools.go`): a pausing call is registered by round and call ID before its `tool` event goes out, and `Answer` (`POST /conversation/answer`) delivers the approval or the client result; waiting calls live in memory.

`chronicle` (`features/chronicle`, see `documentation/Chronicle.md` › *Built in slice 6*) is Chronicle memory. Tables `Entry` (tenanted and owned; `Type` is a built-in `chronicle.Types` ID, `ParentID` makes the tree, `Status` `active` or `proposed`, `Review` flags it), `EntryLink` (`related`, no direction) and `EntryRound` (`created`/`updated`, with the `Previous` summaries). `chronicleservice` (`/chronicle`: `POST list|get|create|update|delete|link|reindex`, `GET types`) edits them and keeps active entries in LanceDB's `entries` table (`chronicle/store/entrystore`, owner-filtered; unembedded entries are found by keywords, and `Reindex` runs at start and when the provider settings change). The pipeline is seam 3's step functions in `chronicle/steps`: `Candidates` (checked entries and their parents, the `chronicle` source's ranking, the window's last round's pinned entries, one hop of links), `Match` (stage 1 at the `ai.chat.stages` `match` level, JSON-schema output; falls back to the candidates' order) and `Update` (the memory update at the `memory` level: rewrites the used entries' summaries, proposes up to 3 entries). The `chronicle` context provider runs the first two and returns the chosen entries as pinned items with a `Reason`; the `chronicle` round follower runs `Update` and, on 🚫, flags what the round changed. A conversation's checked entries are its `chronicle` context settings (`checked`), and its active entries are its last round's pinned `chronicle` segments. **Sharing** (`MultiTenant.md` › *Built in slice 11*): `POST /chronicle/share {id, target}` shares with the tenant at once (`Entry.Shared = "tenant"`, a `shared` column in the entries table) or asks to share globally (a `ChronicleShare` snapshot, approved by a tenant moderator and then by a different global moderator through `POST /chronicle/shares {queue}` and `/chronicle/moderate`, which copies the entry into the global tenant); `target: ""` stops both. Reads use `chronicle.Visible` (own, the tenant's shared, the global tenant's but one's own copies) and the `chronicle` source also searches the global tenant's table; writes and the memory update use only `chronicle.Owned`, so nobody changes another's entry.

`retrieval` (`features/retrieval`, see `documentation/ContextRetrieval.md` › *Built in slice 5*) is the context retrieval engine. `features/retrieval/fuse` is the one weighted-RRF implementation (`fuse.Fuse`), also used by `indexservice.Find`. `retrievalservice.Retrieve` (`POST /retrieval/retrieve`) embeds the query once (`embed-query`; on failure it uses the keyword ranking alone and sets `VectorSkipped`), runs each `retrieval.source`'s vector and keyword search concurrently (a failing source is skipped), fuses per source with the Lexical↔Semantic dial (`w_vec = (a₁+5)/10`), multiplies by the Chronicle↔Library dial (`axisBase^(±a₂/5)`) and by grounding (`((1+up)/(1+down))^γ`, clamped, from `SegmentFeedback`, per tenant), then merges overlapping chunks of one file, keeps identical text once, and takes segments until Top-K or the budget (`min(budgetShare × window, maxBudgetTokens)`). A segment's `ID` is what fusion matches on, its `Key` what feedback counts against (a library chunk's content hash, so feedback survives reindexing while the text is unchanged). `retrieval.Vote` moves counts from a round's old verdict to its new one inside the caller's transaction. `indexservice.Match` carries the chunk `Hash`. The sources are `library` and `chronicle`; RAG Search searches both by default.

`cognition` (`features/cognition`, see `documentation/Cognition.md` › *Built in slice 7*) is the Cognition Engine. A `cognition.Graph` (nodes with typed pins, edges `{from: {node, pin}, to}`) is its own JSON document; a `NodeType` is a struct (`Title`, `Category`, `Event`, `Config` schema, `Pins` or `PinsFor(config)`, `Run(x *cognition.Exec, in cognition.Values) (Values, execPin, error)`), values pass as Go values and are read with `cognition.Get[T](in, pin)`. `cognition.Resolve` validates a graph. `cognition/engine` (`engine.New(db, registry, config)`, made in `serve.go`) runs one synchronously from an event (`Run(RunArgs{GraphID, Event, Inputs, Trigger})`): exec flow from the event node, pure nodes pulled once per run, Return nodes giving the outputs, limits from the `cognition` section, and every node's calls carrying `Meta.RunID`/`NodeID`. Each run is traced in `cognition_runs` and `cognition_run_steps` (values as JSON per pin, cut to a preview over `maxValueKB`, big integers as strings), written when it ends and purged unless among the graph's last `keepRuns` or younger than `keepDays`. `cognitionservice` (`/cognition`: `GET graphs|node-types`, `POST graph|runs|trace`) serves graphs, resolved pins, problems, runs and traces with usage per node. Chronicle's pipeline runs as the built-in **Personal** graph: the `chronicle` context provider runs its `event.userMessage` chain (Candidates → Match → Return items) and the round follower its `event.reply` chain (Branch → Update → Return changes), so a round makes two runs.

For a smoke test without a Gemini key, the genai SDK honours `GOOGLE_GEMINI_BASE_URL`, so `serve` can be pointed at a local stand-in for the Gemini API (`--gemini-api-key` set to anything).

Documentation and plans: `documentation/` documents what is built, one file per feature (`documentation/Index.md` is a table of them, and `documentation/BuildHistory.md` records the dependencies, the seams and each slice). `documentation/plans/` holds what remains, one file per feature with the same name: the design still to build and a `## TODO` section (open questions with *Decision* lines, what to review after seeing it ★, what is not built yet); `documentation/plans/Index.md` is a table of them with the remaining work in brief, and `documentation/plans/Backlog.md` holds ideas no plan owns yet. When something is built, its description moves from the plan into the feature's document and leaves the plan's TODO. Planned, not built: see `documentation/plans/Index.md`. Notable gaps: MCP and the Nexus tools, OIDC and per-tenant Volumes, the Cognition editing passes and the Nexus, `workbench.subjectDescriber` and `editor.getSelection`, saved Explorer queries and `Stats` charts. In the UI, memory entries are called *Chronicles* and knowledge base volumes *Volumes*.

### Workbench

The workbench (`src/pages/workbench/`) is a `flexlayout-react` host with a `SideBar`: a vertical tab per `workbench.sideView` contribution (`{ title, icon, width?, collapsible?, component }`, given `{ registry, collapsed }`) and the open view beside them; clicking the open view's tab hides it, and a `collapsible` view's chevron narrows it to its own width with `collapsed` set (remembered per view). The **Editors** view (collapsible) lists every `workbench.command` (`{ title, icon?, section?, run({ registry }) }`) that has a `section`, one per line with its icon and title, grouped by section in the order of their first command; collapsed, it shows only the icons, the title as tooltip. Its model is built on first render, after discovery. Its borders come from `workbench.borderTab` contributions (`borders.ts`: one border per location that has tabs, all collapsed; later contributions join an existing border, and a removed one's tab is deleted); each border tab's component is `borderTab`, rendered by `BorderTabHost` from the contribution. Adding a border tab is only a `contributions.ts`. Editors are `workbench.editor` contributions (`src/workbench/points.ts`), and are never opened directly:

1. A sidebar icon creates an object (e.g. `new VolumesObject('volumes')`) and calls `EditorRegistry.edit(object)`. An object is any `EditableObject` (`{ kind, id, name?, helpText? }`).
2. `EditorRegistry` derives the tab id `<kind>:<id>` (`tabIdOf`); if that tab is open it is focused, otherwise a new tab is added with the object in its `config`. The tab text is the object's `name` if it has one (else `<editor name> <id>`), and its hover text the object's `helpText`.
3. `ComponentFactory.tsx` renders border tabs with `BorderTabHost` and every other tab with `EditorHost`, which finds the `workbench.editor` contribution whose id is the object's `kind` (or shows a placeholder) and renders it with `EditorProps`: `{ object, registry, tabId }`. Editors that open other editors use `registry`.

Adding an editor: create `src/editors/<name>/` with the object, the editor (taking `EditorProps<YourObject>`) and a `contributions.ts` calling `extensions.contribute(editors, { id: '<kind>', source, name, component: lazy(() => import('./<Name>Editor.tsx')) })` and, to list it in the Editors view, `extensions.contribute(commands, { id: 'open-<kind>', source, order, title, icon, section, run: ({ registry }) => registry.edit(new YourObject(...)) })`. `EditorRegistry` also has `rename(tabId, name)` and `close(tabId)`.

**Workbench context** (`src/workbench/context/`, see `documentation/WorkbenchContext.md` › *Built in slice 4*): `workbenchContext` (`WorkbenchContextStore.ts`) is this browser tab's record of the open editors, what each is editing, the focus order and the 20 most recent subjects (`viewed`, `edited`). `Workbench.tsx` feeds it the layout's tabs and focus through a flexlayout change listener (border tabs excluded); editors report what they edit with `useWorkbenchSubject(tabId, { type, id, label, summary? }, { selection, dirty })` (`WorkbenchContext.ts`), and `store.touch(tabId, 'edited')` for edits. Markdown, Volume, Volumes and the Log Explorer report; Markdown's selected lines come from Live Preview and Source through `CollabSession.setSelection`. Chat sends `store.snapshot('main', tabId)` (about 4 KB: references, labels and selections, never content; `previous` is the tab focused before the chat) while the conversation's Context control is on; the server's `workbench` provider renders it with every label quoted as data.

Side views: **Editors** (its sections, from the commands, below), **Cognition** (the Explorer: graphs by kind; opens the Cognition Editor) and **Chronicles** (`src/chronicle/ChroniclesView.tsx`): the memory entries as a tree per type, a checkbox per entry for the focused chat's conversation (a checked child shows its parents checked), a dot for entries used in the last reply, ✎ for those the last memory update changed, ⚑ for flagged ones, and a *Proposed* group to accept or dismiss. Clicking an entry opens the entry editor (title, type, parent, the type's fields, the summaries, the full context, related entries, and the rounds that changed it, with *Restore earlier summaries*; *Share…* opens `src/chronicle/ShareChronicleDialog.tsx`). Entries others shared are listed under *Shared with you* and open read-only.

Editors view sections:

- **AgentOS** - Chat (`src/editors/chat/`, `new ChatObject()`, tab `chat:main`): a continuous scroll of conversations that opens on the latest one and continues it (✕ on its divider or `/new` starts another; scrolling up loads earlier ones), with the level toggle (hover: model and estimated input cost), the ⚙ context settings, `/` commands and Stop. Replies render with `MarkdownText` with citation chips; below a reply are its Chronicle chips (the pinned entries; a chip opens the entry), its Sources row and Context inspector (when segments were injected; the inspector's *Why* is a pinned segment's `reason`), the memory update's line and, on hover, 👍/👎/🚫 and the footer (level, model, tokens, cost, latency). A citation opens the cited file with its lines selected (`openMarkdownAt` in `editors/markdown/openMarkdown.ts`, asking through `editors/markdown/reveal.ts`, which Live Preview reads once the document has loaded). Dashboard (`src/editors/dashboard/`, `new DashboardObject()`, tab `dashboard:main`): the `dashboard.widget` grid, starting with *Usage & cost*. Cognition (`src/editors/cognition/`): opens the built-in Personal graph in the Cognition Editor.

- **Knowledge** - New Chronicle (opens an empty entry editor), and Volumes: manages Knowledge Base Volumes. `VolumesEditor` browses the knowledge base root through the `Volume` client: double-click a folder to open it, breadcrumbs to go back, and toolbar actions to make a folder, remove an empty non-volume folder, or convert the selected folder to a volume. Double-clicking a volume does not enter it but opens it (`openVolume`, via `KnowledgeBase.openVolume`) in a `VolumeEditor`.
- **Administration** - Tenants (`src/editors/tenants/`: members with their roles, *Roles…* opening the Share dialog on the current tenant) and Users (`src/editors/users/`, with the *Super Administrator* and *Full logging* switches), Roles (`src/editors/roles/`, the Role Editor: roles with their permission matrix and grants, custom tenant roles, and the Access checker; `ResourcePicker`) Moderation (`src/editors/moderation/`, the queue of global Chronicle shares) and Secrets (`src/editors/secrets/`, with `secret.list` on `app`: server secrets and the app scope's secret settings, each with *Set…* in a password dialog and *Delete*; never a value), each shown by permission through `canIn` (the Volumes command shows only in tenant `1`). `src/components/share/ShareDialog.tsx` (helpers in `grants.ts`) lists and edits the grants on one resource, with those inherited from above; the Volumes editor's *Share volume* opens it. Account (`src/editors/account/`, kind `account`) opens from the account menu. Log Explorer (`src/editors/logs/`, `new LogsObject('explorer')`): searches the stored logs over a time range with a structured builder (`builder.ts`: `toLogsQL`, and `fromLogsQL` for what it can show) or LogsQL in Monaco (`logsql.ts`: tokenizer, completion, parse-error markers); a level-stacked hits histogram (drag to zoom), virtualized `LogRow`s with quick filters, trace and surrounding-record links, stats as a table, and live tail. Every run writes a deep link (`/workbench?logs=<query>&range=1h`), which `Workbench.tsx` opens on load; other views open the Explorer with `openLogs(view)` (DevTools' Log tab does, for a record with a trace), and `logsOn(view)` gives one tab per query and range.

`VolumeEditor` (`src/editors/volume/`) edits a `VolumeObject`: id `volume-<tsid>`, plus the `tsid` and the `path` of folders from the root. Its tab text is the volume's folder name and its hover text the full path, the root being `/` (e.g. `/projects/veritas`). It browses the volume's subfolders and makes folders and files; the new-file dialog always asks for the file type, from `fileTypes` in `Volume.ts`. Double-clicking a markdown file opens it in a `MarkdownEditor` (`openMarkdown`, via `Collab.openFile`).

`MarkdownEditor` (`src/editors/markdown/`) edits a `MarkdownObject`: id `markdown-<fileId>`, where `fileId` is the file's collaboration room. It is a nested flexlayout (one `Model` per editor) with three views of one shared Yjs `Y.Text`: **Live Preview** (Obsidian-style, CodeMirror 6), **Source** (Monaco) and **WYSIWYG** (Milkdown); see `documentation/MarkdownEditor.md`. `collab/CollabSession.ts` owns the `Y.Doc`, awareness and connection (`start`/`stop` from `useCollabSession`); `MarkdownStatusBar` shows connection, save state and peers. Views are lazy-loaded chunks. **Source** (`source/SourceView.tsx`) bundles Monaco locally (`source/monacoSetup.ts`, no CDN) and binds it with `y-monaco`; `vite.ts` (the `foundation()` plugin) dedupes `monaco-editor`/`yjs` and aliases the `editor.api.js` path y-monaco imports, which monaco-editor 0.57's exports map no longer allows. **Live Preview** (`live/`) is CodeMirror 6 with `y-codemirror.next`: `livePreview.ts` hides markdown syntax on lines the selection is not on and renders checkboxes, bullets, links, images, rules and callouts in place; `obsidianSyntax.ts` adds `[[wikilinks]]` and `#tags` to the parser; `obsidianTheme.ts` styles it from the MUI theme. The two bindings publish cursors under different awareness fields (`cursor` vs `selection`); `collab/cursorBridge.ts` records which is current in `cursorFrom` and the provider copies it across for remote states, so cursors show in every view. **WYSIWYG** (`wysiwyg/`) is Milkdown (commonmark, gfm, history, listener) with a formatting toolbar. Milkdown's collab plugin needs a `Y.XmlFragment`, so `yTextBridge.ts` syncs through markdown instead: local edits go to the `Y.Text` as a diff-match-patch patch from the last synced serialization (so Milkdown's normalisation never rewrites text the user did not touch), and remote changes reload the document outside the undo history, keeping the cursor by textblock and offset. It shows no remote cursors.

### Volumes

A volume is a folder under the knowledge base root (`--kb-root`, default `~/.foundation/kb`) containing a `.volume.json` marker (`volumeservice.Marker`) with its TSID. Folder names cannot contain `.`, so the marker never collides with a folder and dotted entries (the marker, index sidecars, temp files) are never listed. `CreateFile` and collab saves publish a `volumeservice.FileEvent` on `FileEvents`, which the index subscribes to. `kbservice.OpenVolume` returns the marker's ID. `RemoveFolder` only removes empty folders that are not volumes, so it never deletes content. `CreateFile` creates a file (empty, or with `Content`) only inside a volume, of a type in `volumeservice.FileTypes` (currently only `markdown`, `.md`); the frontend's `fileTypes` mirrors that list. `ListFolder` returns folders and files of known types (`kbservice.SplitFile`). Error messages name folders relative to the root, never by server path.


### Collaboration

`collabservice` (`/kb/collab`) lets several users edit one volume file. `OpenFile` (`POST /kb/collab/files/open`) returns the file's room ID, the same for everyone; `GET /kb/collab/files/:fileId` upgrades to a WebSocket (`github.com/coder/websocket`) speaking the y-websocket protocol (sync 0, awareness 1) plus our control messages (100, JSON: `role`, `seeded`, `ready`, `save`, `saved`, `compact`, and `edit`/`edited`, by which `EditFile` has the writer apply a tool's find/replace edits to the shared text (`collab/edits.ts`, the same rules as `collabservice.ApplyEdits`: each find exactly once); 101 compacted state). The server relays Yjs updates and keeps them as an opaque log; it never decodes the CRDT. The oldest connection is the **writer**: it seeds a fresh room from the file and autosaves (1s debounce); the server writes the file atomically via a dotted temp file. `OpenFile` and the WebSocket need `volume.read`; without `volume.write` the file is read-only (`readOnly` in `OpenFile`'s response, the editors open read-only): the room drops that connection's updates (except a writer's seed), ignores its saves, never sends it `edit`s, and a writable connection that joins takes the writer role. Empty rooms are dropped after 30s; connecting to a dropped room closes with 4404 and the file must be opened again. Services share the volume path helpers in `volumeservice/Files.go`. The frontend side is `src/services/Collab.ts` and `src/services/collab/CollabProvider.ts`; WebSocket traffic is logged under the `collab` domain, not captured in DevTools' Network tab.
