# Infrastructure as Code

Forge iteration 22 (`../forge/documentation/plans/022-InfrastructureAsCode.md`): the deployment as versioned configurations in the root tenant, planned against what exists and applied by durable jobs through the Control Plane ([ControlPlane.md](ControlPlane.md)). The backend is here, in `features/infra`; the Infrastructure app's pages are Forge's.

## Built in forge 22a to 22f

### Configurations (22a, `features/infra`)

- A configuration is a definition family on the `def` stream, target type `infraConfig`, one configuration `main` (`infra.DefaultConfig`); only the root tenant may hold one (`not_root_tenant`). Its `Document` holds keyed lists, each sorted by id: `accounts` (a provider and a connection id, never a credential), `sites` (an account and region, or `onPremise`), `clusters` (one per site), `hostPools` (size and count at a site), `profiles` (container or VM, image, packages, units, files), `stacks`, `placements` (a stack or a profile, a count per site), `overrides` (a tenant's spec) and `settings` (`onDrift`: `report` or `correct`). `Document.Check` refuses bad references, duplicate ids and bad values with problems at `document.<kind>[<id>].<field>`.
- Ops (each with its inverse, in `infra`'s own `TestEveryOpUndoes`): `infra.config.put {kind, item}`, `infra.config.remove {kind, id}` (refused while something refers to the item), `infra.config.settings`, `infra.config.import {document | files, force?}` (`draft_dirty` unless `force`). `infra.config.commit {message, expect}` freezes the draft as an immutable `infraVersion` (`<config>-<n>`, projection `infra.version`) in the same batch (`head_moved` when the draft moved, `nothing_to_commit`; not undoable, `NoBranch`); the internal `infra.config.markApplied {number}` records what an apply reached. Queries: `infra.config`, `infra.versions`, `infra.version {number}`.

### Diffs, export and import (22b)

- `text.DataDiff(a, b, keys)` (`features/text/Data.go`) compares JSON values as things: `added`, `removed`, `changed`, and `moved` for a keyed item that changed place, at paths like `hostPools[general].count`; keys name the lists matched by a field (`{"sites": "id", "profiles[].units": "name"}`). The *Data diff* node (`data.diff`, `textnodes`) gives it to graphs.
- `infra.Diff(a, b)` adds the list, the item and a summary (*host pool general on west: count 3 → 5*); the `infra.diff {from?, to?}` query follows the draft (`{}` is what the draft changes since its head).
- `infra.Export` writes a version as YAML files: `config.yaml` (accounts, profiles, overrides, settings), `sites/<id>.yaml` (a site with its cluster and host pools), `stacks/<id>.yaml`, `placements.yaml`; `infra.Import` reads them back, refusing unknown files and fields. Both refuse, by path, anything that is or looks like a secret (`secret_in_config`: a `$secret`, `$ref` or `$vault` placeholder, a JWT, a NATS seed, a PEM private key). The `infra.config.export {version?}` query gives `{files}`; `infra.config.import {files}` reads them.

### The compute contract and the Infrastructure test server (22c)

- `infra.compute@1` (`infra.ComputeContract`, a Go builtin passing `CheckContract`; golden tool shapes in `features/infra/testdata/golden`, rewritten with `go test ./features/infra -update`): `host.create` (keyed by `id`, our name for the host: a second create makes nothing), `host.get`, `host.list`, `host.start`, `host.stop`, `host.delete` (destructive, idempotent), `size.list` (`vms` when a size can run VMs), `image.list`, `region.list`, `check`, and the `host.changed` event (delivery `watch`). A type makes whatever a host needs inside `host.create` and removes it in `host.delete`.
- `features/infra/infratest` is the Infrastructure test server: the builtin type `infratest` implementing `infra.compute@1` over hosts kept **in the serving process's memory** (sizes `s`, `m`, `l`, `xl`, the last two with `vms`; regions `r1`, `r2`), a host `creating` until the connection's `delayMs` passes, `host.changed` from its `Watch`, and failure injection through its own contract `infratest.control@1` (`fail {operation, times, kind}`, `slow {operation, ms}`, `vanish {host}`, `state`). `serve.go` serves it in-process (`infratest.Default.Impl()`).
- `features/infra/contracttest.Run(t, call, Options)` is the suite every compute type passes: keyed create, list finds it, it becomes running, delete is idempotent and leaves it gone.

### Resources and plans (22d)

- A document expands into resources (`infra.Resource`: id, kind, site, account, props, dependencies, `needsVms`, `holdsData`) by the kinds on the `infra.resourceKind` point (`infra.ResourceKinds`, declared in `serve.go`): `host` (`host:<site>/<pool>/<n>`, made at the provider as `<site>-<pool>-<n>`, compared on size, region and image), `cluster` (`cluster:<site>`, after its hosts) and `instance` (`instance:<site>/<placement>/<profile>/<n>`, after the site's cluster). Later parts add kinds there.
- `infra.ReadActual` lists each account's hosts and sizes through `infra.compute` (over `Deps.Compute`, `infra.DispatcherCompute` in `serve.go`) and asks `Deps.Actual` for the rest (`infraapply.RecordsActual`: instances by their desired-state records, a cluster once one of its hosts is recorded).
- `infra.Plan` (pure) gives steps `{id, op: create | change | remove, kind, site, account, before, desired, after, holdsData, summary}`: removals first, dependents before what they depend on, then creations and changes in dependency order; **refusals** for a VM where no host of the site can run VMs (*no host on west can run VMs*) or a host size without `vms` that must have it; **notes** for a cluster of fewer than three hosts.
- The `infra.plan {config?, version?}` tool (`infra.MakePlan`) stores the plan as an `infraPlan` on the live area `infra` (internal `infra.plan.record`; status `ready`, or `refused` with refusals), read by `infra.plans` and `infra.planOf {id}`.
- `infra.plan` checks `infra.operate` and never asks (it changes nothing at the providers), so a page's *Call tool* and the chat plan freely; applying is the person's decision. `infra.LoadDocument` reads the draft or a version, waiting a little for one committed a moment ago.
- `infra.describe {config?, version?}` (`infra.Describe`, read, `infra.read`): a version (left out: the applied one, else the head; 0 the draft) as resources by site, each `present`, `missing`, `changed` or `extra` by the plan against what exists, which it does not store; with refusals, notes and counts (forge 22q).
- `infra.RegisterToolAndCall` registers a tool and a live call of the same id ending with one `result {content, summary}`: `infra.plan`, `infra.describe` and `infra.drift` are both, so the forge tools call them over the live connection.
- `infra.versions` watches every version and keeps the configuration's (a KV pattern matches whole tokens, so `main-*` matched nothing).

### The infrastructure nodes (22e, `features/infra/nodes`)

*Ensure host* (`infra.ensureHost`), *Ensure instance*, *Ensure unit*, *Ensure packages*, *Wait healthy* and *Remove*, each External, for function, server action and trigger graphs. They write the Control Plane's desired state, the infrastructure app's records (`infraHost`, `infraProfile`, `infraInstance`, `infraUnit`, `infraPackagePin`), under ids derived from resource ids (`infranodes.RecordID`: `host:west/general/1` → `host_west_general_1`), changing only what differs, with command ids derived from the record (`Nats-Msg-Id` drops a repeat): run twice, they change nothing. A host is made through `infra.compute` first. The same logic is Go (`infranodes.EnsureHost`, `EnsureInstance`, `EnsureUnit`, `EnsurePackages`, `WaitHealthy`, `RemoveStep`) for the apply.

### Apply, drift and rollback (22f, `features/infra/apply`)

- `infra.apply {plan}` (`infra.admin`) refuses a plan with refusals (`plan_refused`), one older than 15 minutes (`plan_stale`, `infraapply.PlanMaxAge`) or one applied already (`already_applied`), and makes an `infraApply` (id: the plan's) on the `infra` area. Each step whose steps are done is enqueued as a job of the built-in graph `infra-apply-step` (*Run apply step*, `infra.applyStep`), id `apply-<apply>-<record id>-<attempt>`, queue `infra`, keyed by site; a removal of what holds data becomes **proposed** instead and waits for `infra.apply.approve {step}` (`infra.approve`).
- A step's job runs `infraapply.RunStep`: a retryable provider error fails the run so the job retries; otherwise the outcome is recorded by the internal `infra.apply.step`, whose decision enqueues the steps it unblocks **in the same commit**, so whichever runner finishes the last dependency enqueues the next, and no leader is needed. A step not ready does nothing. The last step marks the version applied.
- `infra.apply.resume` runs failed (and stuck) steps again as new attempts. `infra.applies` and `infra.applyOf {id}` read applies.
- `infra.drift` (`infraapply.CheckDrift`) plans the applied version against what exists; with `onDrift: correct` it applies that plan. Rollback is planning and applying an earlier version.
- The step jobs a commit names are enqueued by the `infra` area's outbox follower, which the apply commands make sure is followed first (`infraapply.Deps.Outbox`, `jobs.Runner.Outbox` in `serve.go`).
- `infra.topology {config?}` (`infraapply.Topology`, a live query): the applied version (else the head, else the draft) as resources by site, each `present` or `missing` by the Control Plane record it is made as (`extra` for an `infraHost`/`infraInstance` record made by an apply that no resource names any more), with the record's health and status; it follows the configuration, the versions and the records and sends the whole view again when it changes (forge 22p).
- `serve --control-plane` on a fresh server makes the root tenant before anyone exists; the next start gives it user 1 as Owner while it has no member (`controlplane.EnsureRootTenant`), else `cli controlplane init --user 1`.

## Built in forge 22h (in part): NATS nodes and gateways
- Two more kinds on `infra.resourceKind`: `natsNode` (order 22, holds data) and `gateway` (order 24). Each site with a cluster gets `natsNode:<site>/<n>` for n up to the cluster's `natsReplicas` (three when 0), never more than its hosts, placed on the site's hosts in turn and depending on the cluster and that host. Sites are joined by `gateway:<a>~<b>` (ids in order): `gateway` between two cloud sites, `leaf` from each on-premise site to the first cloud site by id (Tony to confirm), depending on both sites' nodes.
- A node's properties carry its site's whole NATS cluster as the configuration gives it (`peers`, the nats unit records `natsNode_<site>_<n>__nats`; `gateways` `[{name, urls}]` with `nats://nats-<site>-<n>:7222`; `leafRemotes` `[{url, urls, hub}]` with `nats-leaf://…:7422`), all compared, so a node is `changed` when its site or a joined site grows. `infranodes.EnsureNatsNode` (run by *Run apply step*) ensures its instance (`natsNode_<site>_<n>`, named `nats-<site>-<n>`, profile `nats`, on its host's record), its unit of kind `nats` and the site's `infraNatsCluster` record `nats_<site>` written whole (`name`, `site`, `nodes`, `gateways`, `leafRemotes`), the same values from every node of the site, so the nodes may run in any order and at once. A gateway's step does nothing of its own: it is there once either site's record names the other (`infraapply.Joined`).
- `RecordsActual` reads a node from its instance record and its site's cluster record, and a gateway from the records; `infra.topology` also follows `infraNatsCluster`. Removing a node removes its unit and instance records. `infra.RecordID` is now the one record id function (`infranodes.RecordID` calls it). Tested by `infra` `TestNatsTopology` and `infra/apply` `TestNatsClusters`.
- Not built: forming the LXD cluster (`lxd init --preseed`, join tokens, evacuation), its storage and network, and removing a site's cluster record with its last node; these wait for a real LXD (22g).

## Built in forge 22o (in part): the seed
- `backend/scripts/infra/seed/seed.sh` (with `lib.sh`, shellcheck clean) is the one step run by hand. `--adopt` runs on the machine it is to use; `--provider lxd` makes a VM on this machine's LXD (`--vm -c security.nesting=true`), copies itself in and runs there as `--adopt` (azure, digitalocean and fly come with 22l to 22n; iteration question 12 decided this way to go on, Tony to confirm). Each step checks before it acts: the `lxd` snap, `lxd init --preseed` (a directory pool and `lxdbr0`), the instances `nats-<site>-1` and `server-<site>-1`, the first-party apt source and key on `--channel`, `nats-server` and `axiomd` in the NATS instance (its packaged unit enabled), `--package` (default `axiom-server`) and `axiomd` in the server instance, the unit `axiom-seed-serve` running `<server-bin> serve --control-plane`, the first administrator through `/identity/setup` while the server is single-user (the password read once from stdin and passed on stdin, never on a command line; serve restarted so the root tenant gets its Owner), and the first configuration (an on-premise site with a cluster of one NATS replica, a host pool of one `seed` host, a `server` profile placed once) committed as version 1 and marked applied by `--import-cmd` (default `<server-bin> infra import`; `forge infra-import` with Forge's package). It ends by printing where to sign in. Plan question 2 is answered as proposed: the administrator through `/identity/setup`, no new command to make one.
- `cli infra import <dir>` (`infracli.ImportCommand`, which Forge adds as `forge infra-import`) signs in (password on stdin), switches to the root tenant and runs `infra.SeedDraft`: `infra.config.import` of the folder's YAML files (22b's format) and `infra.config.commit`, which now takes `applied` to mark the new version applied too; with the same files again it commits nothing. It talks to serve with `features/live/liveclient`, the live client Forge's developer tools had (moved here; Forge's `devtools/client` now aliases it).
- `infra/seedcheck` runs the seed twice against fake `lxc`, `lxd` and `snap` that keep their world in files (embedded in the package), and reports each run's changing calls and whether the password reached a command line or the output; `go test ./features/infra/seedcheck` checks both modes and a refused `--site`, and Forge's `forge seed-check` runs the same.
- Not built: putting the first secrets into Vault (the operator runs `scripts/secrets/` after the seed), serve on the NATS instance instead of its own JetStream (22i's bootstrap), `--join <token>` for adopting more on-premise machines, and the seed's host and instances as Control Plane records (enrolling `axiomd`), so the first plan still lists them as missing.

## Built in forge 22i (in part): serve units checked from the services' manifests
- `infra.Services{Specs, Groups}` is what serve units may name (`infra.Deps.Services`, given by `serve.go` from the service catalog, Forge's too, and `serviceGroups()`). `Services.Access(unit)` reads a `serve` unit's set as `serve --services` does (`services.ParseSet`; `all` is every service, `connectors:<type>` items are kept out of the check) and gives its `UnitAccess`: the services, its NATS permissions (`services.ProcessPermissions`) and the Vault paths its services' manifests name.
- `infra.CheckUnits(doc, services)` (run by `MakePlan`) refuses, on the placement's first instance, a service a placed unit runs that calls a service no unit serves on the same site (*web calls records, which no unit serves on site west*), unless the settings' new `crossSite` names the callee and the site has a gateway to a site serving it (question 2 as proposed, Tony to confirm); a unit naming what `--services` does not take is refused on its profile (`profile:<id>`). The plan record carries each profile's units' access as `units`, for a reviewer. Question 1 as proposed: 21g's groups plus explicit lists.
- `Settings` gained `crossSite` (set whole by `infra.config.settings`), so settings compare with `Settings.Equal`. Tested by `infra` `TestServeUnits`.
- Not built: the issuer still gives every set `natsauth.Everything` and the bootstrap policy (`serve.go`'s `unitSet`), not the permissions and policy the check computes; restarting a unit whose set changed and revoking its old user; the Plan page showing units' access.

## Built in forge 22j and 22k (in part): built-in stacks and a tenant's own instances
- `infra.StackTemplates()` and the tool and call `infra.stackTemplates` (read) give the built-in stacks, each `{stack, profiles}` to copy with `infra.config.put`: *Server* (`server-web` running `web`, `server-data` running `data`), *Runners* (`runner`) and *Mail workers* (`runner` plus `connectors:mail`). A stack owns its profiles and a placement chooses only where and how many (22j question 1 as proposed, Tony to confirm). The NATS cluster is not a stack: its nodes come with each cluster (22h). Tested by `TestStackTemplates` against the real catalog; no service's manifest declares a call to another yet, so the unit check refuses nothing there.
- An override's `spec` now has its first switch, `runners {profile | stack, sites, vm}` (`Override.Switches`, checked: a tenant other than the root, a stack or a profile, known sites; unknown switches are refused): the tenant's own instances `instance:<site>/tenant-<t>-<override>/<profile>/<n>` with the `tenant` property, each `kind: vm` and needing a host that runs VMs when `vm` (so the plan refuses *no host on west can run VMs*). Tested by `TestTenantRunners`.
- Not built: the instance record carrying its tenant and its units' NATS users holding only that tenant's account; own clusters, own databases with their routing entries and migrations, and stream placement (iteration question 7 and 22k's question 1 are open); stack graphs with parameters; placement constraints beyond `requiresVms`; the Stacks and Placements pages.
