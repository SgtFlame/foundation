# Control Plane

The runtime of forge iteration 20 (forge `documentation/plans/020-ControlPlane.md`). It takes Foundation from one process with embedded NATS to clustered NATS with accounts, daemons on LXD hosts and in instances, and the credentials those daemons and the services they start run with. It is built part by part. Each part below says what it built; the plans hold what remains.

Deployed NATS itself (cluster URLs, credentials, TLS, replicas for every stream) is forge 20a-1, documented in [Live.md › Built in forge 20a-1](Live.md#built-in-forge-20a-1-deployed-nats).

## Built in forge 20a-2: Operator, accounts and credentials

`features/controlplane/natsauth` makes the deployment's NATS authorization as **decentralized JWTs**, as decided in forge 20 question 5. It uses `nats-io/jwt` and `nkeys` directly, with no `nsc` binary.

- **Deployment** (`natsauth.Init(operator)`): an operator plus the accounts `SYS` (the system account), `CTL` (the control account, carrying `ctl.>`) and `APP` (every tenant's streams until forge 20a-3). Each account has its own signing key, which signs its users. `AddAccount(name, Limits)` makes further accounts, such as a tenant's. `Account.SetLimits` covers connections and JetStream storage, memory and streams, with zero meaning unlimited. `Account.Revoke(userKey)` revokes a user, and `Operator.Sign` re-signs an account after a change.
- **Users** (`Account.NewUser(name, Permissions{Pub, Sub, Responses}, ttl)`): a user JWT and a creds file. An empty direction denies everything in that direction, and `natsauth.Everything` allows every subject in the account.
- **Servers** run the **full resolver**. `Deployment.ServerConfig(dir)` renders the lines every `nats-server.conf` includes: `operator`, `system_account`, the resolver, and `resolver_preload` holding every account. Account changes are pushed with `natsauth.Push(sysConn, account)` over `$SYS.REQ.CLAIMS.UPDATE`, with no restart and no file edit. A pushed revocation disconnects the user at once.
- **Keys** (`natsauth.Keys`): `Deployment.Save`/`Load` keep the operator seed, each account's keys and JWT, and the account list. `DirKeys(dir)` stores each as a file with mode 0600. A deployment loaded without `operator.nk` still mints users but cannot re-sign accounts, so the operator seed may be kept offline (part question 1). Keeping these keys in the SecretStore comes with the credential issuer (forge 20h).
- **CLI**:
  - `cli nats init --keys <dir>` makes the deployment and writes `trust.conf`, `serve.creds` (an `APP` user) and `sys.creds` (a `SYS` user for pushing).
  - `cli nats user --account --name` prints a new user's creds file.
- **Tests**: `natsauth.StartTestSecure(t)` runs an in-process server with a fresh deployment, using JetStream, a listener and the rendered configuration. `CredsFile`, `Conn`, `Serve` (`natsd.Start` with an `APP` user) and `System` connect as users. The tests cover:
  - a `CTL` user's subjects never reach an `APP` user;
  - `serve`'s user has JetStream in `APP`, and `CTL` cannot read it;
  - a user scoped to one host's subjects gets a permissions violation on another host's;
  - a pushed account accepts its users at once;
  - revoked and expired users are refused.

## Built in forge 20a-3: An account per tenant

With a deployment's keys, each tenant's streams and buckets live in **that tenant's own NATS account** (`T<id>`, `natsauth.TenantAccount`), so an account boundary and not only a name prefix keeps tenants apart. Names keep their tenant suffix inside the account, so nothing that parses them changed, and development (embedded NATS, one account) works as before.

- **`natsd.Accounts`** (`For(ctx, tenant) jetstream.JetStream`) gives a tenant's JetStream. `natsd.Single` is one JetStream for every tenant; `natsd.NewPerTenant(opts, creds)` connects to each tenant's account on first use with the creds `creds(ctx, tenant)` returns, and keeps the connection (`Close` closes them all). `natsd.For(ctx, acc, js, tenant)` is `js` when `acc` is nil.
- **Who uses it**: `project.Projections.SetAccounts` and `JetStreamFor(ctx, tenant)` (event streams, projection and side buckets, folds, atomic batches; the bus and `Transact` publish through it), `jobs.Runner` (the `JOBS_<tenant>` queue, its schedules, the tenant's event streams for triggers), and `SetAccounts` on `presence.Presence`, `activity.Store`, `ui.KVSessions` and `recordsfiles.Store`. Constructors are unchanged. Without `SetAccounts` every tenant uses the shared connection.
- **What stays in `APP`** (the services account, part question 1): every connector state, `cx.call.…`, `cx.resolve`, `cx.status`, `cx_adapters`, `cx_sources`, `cx_leases`, ledgers, cursors, locks, secrets placeholders, discovered contracts and the `CX_<tenant>` event streams, until the services split (forge 21e). `Projections.JetStream()` is that shared connection; `natsd`'s `TestSharedJetStreamOnlyForServices` refuses its use outside the connectors.
- **Accounts**: `Deployment.AddTenant(id, Limits)` makes a tenant's account (unlimited by default, part question 2), `TenantOf(name)` reads an account name back. `SaveAccount` adds a new account to the account list. `natsauth.Minter(d, keys, name)` mints `serve`'s user in a tenant's account (every subject, no expiry), looking in `keys` again for an account added after it loaded.
- **serve**: `--nats-keys <dir>` (or `$FOUNDATION_NATS_KEYS`; `natsauth.TenantAccounts(opts, dir)` makes the `PerTenant`, as both serves call it), the directory `cli nats init` wrote, turns per-tenant accounts on; serve connects to `APP` with `--nats-creds` as before and to each tenant's account with users it mints. A tenant without an account fails its live core with `no_tenant_account`.
- **CLI**: `cli nats tenant add --keys <dir> --tenant <id>` makes and saves the account (it needs `operator.nk`) and, with `--nats-url`, pushes it to the running cluster as a `SYS` user (`<keys>/sys.creds` unless `--nats-creds`).
- **Tests**: `natsauth`'s `TestTenantAccountsKeepStreamsApart` (on `StartTestSecure`, two tenants: the live core makes tenant 10's event stream in `T10`, where neither `APP` nor tenant 11 sees it, and tenant 11 publishing on tenant 10's subjects reaches no stream) and `TestMinterFindsNewAccounts`.

## Built in forge 20a-4: Gateways, leaf nodes and placement

Several JetStream clusters, one per LXD cluster, are joined by **gateways** into a supercluster; on-premise sites join a **hub** cluster as **leaf nodes**; and a tenant's streams are **placed** in a chosen cluster.

- **Placement per tenant** (`natsd`): `SetTenantPlacements(func(tenant) (Placement, bool))` places a tenant's streams, KV buckets and object stores, which `Stream`, `KV` and `Object` find by the tenant id in their names (`TenantOfName`: the first all-digit token between underscores, so `EVT_5_def`, `PRJ_5_…`, `cx_secrets_5`, `FILES_5` are tenant 5's). A config's own placement wins, then the tenant's (its replicas, else the default's), then the default. `serve --nats-placements 5=b,7=a` (or `$FOUNDATION_NATS_PLACEMENTS`, `ParsePlacements`) sets them until the root tenant's desired state does (forge 20b-2).
- **Moving a tenant** (`natsd.Place(ctx, js, tenant, Placement)`, `cli nats place --tenant --cluster [--keys]`): every stream of the tenant gets the new placement, one at a time, waiting until it has every replica current in its new cluster (`placement_timeout` after two minutes); JetStream moves the messages and none is lost. A stream already there is left alone. With `--keys` it reaches the tenant's own account (20a-3).
- **Gateways** are each node's configuration (its cluster's name, the other clusters' gateway URLs). They become desired state in forge 20e; until then they are written by hand, as the fixture does. Gateways and leaf nodes need a system account on every node.
- **Leaf nodes**: a site's nodes connect out to the hub's leaf port and run JetStream in **their own domain** (`jetstream.domain`), so a site's streams stay at the site and keep committing while the link is down; the hub reads them through the domain (`jetstream.NewWithDomain`). A site is one leaf node, or a cluster of its own whose nodes each hold a leaf connection (iteration question 4). The hub is the root tenant's cluster (part question 1); a second hub for failover comes with desired state (20e).
- **Fixture**: `natsd.StartTestSupercluster(t, clusters, size)` (clusters `a`, `b`, … joined by gateways; the first is the hub, `Hub()`), `Supercluster.StartTestSite(name, domain, n)` (a `Site` with a `Link`, a TCP relay standing for its network link, `Cut()` and `Restore()`), `Cluster.Name()` and `NodeName(i)`.
- **Tests** (`natsd`): `TestTenantPlacedInACluster` (a client of cluster `a` makes tenant 5's stream in `b`, where it is placed; `Place` moves it to `a` with all ten messages, and a second run moves nothing; another tenant's stream is not placed) and `TestSiteKeepsCommitting` (a one-node and a three-node site commit while cut off, the hub's requests to the site fail with no responders or a timeout, then succeed once the link is back).

## Built in forge 20b-1: The root tenant and infrastructure roles

- **`features.RootTenantID`** (3, iteration question 3) is the reserved **root tenant**, *Infrastructure*, the only tenant that may hold infrastructure. It is a real tenant row made by `controlplane.EnsureRootTenant(ctx, appDB, owner)`, by `serve --control-plane` (its Owner user 1 when that user exists) or by `cli controlplane init --user <id>` (run again to add an Owner, `controlplane.AddRootOwner`). Setup never makes it, `tenantservice.Delete` refuses it (409 `root_tenant`), and the tenant switcher shows it only to its members, as for any tenant.
- **Pinned resource types** (`authz.ResourceType.Tenant`): a type pinned to a tenant has its actions held only on resources in that tenant and only through grants made in it. Neither a role granted in another tenant nor the Super Administrator's grant on `app` reaches (part question 1: the root tenant's Owner is whoever set up the control plane, and no one else by default).
- **`controlplane.ContributeAccess`** (both serves call it) declares the type `infra`, pinned to the root tenant, with `infra.read` (`read`), `infra.operate` (`execute`), `infra.admin` (`admin`), `infra.enroll` (`create`) and `infra.approve` (`moderate`), and the contributed roles *Infrastructure viewer* (110, `read`), *Infrastructure operator* (111, adds `operate`) and *Infrastructure administrator* (112, all). The root tenant's *Owner* and *Administrator* hold them by class as usual.
- **Forge's tools**: `forge grant --tenant root` and `forge users`' `tenantIds` take `root` for tenant 3.
- **Tests** (`controlplane`): the root tenant is made once with its Owner, who holds every `infra` action; a non-member and the Super Administrator hold none; a viewer reads and does not operate; the administrator role granted in tenant 1 holds nothing, there or in the root tenant; an added Owner approves.
- Not built: the browser's `useCan()` (`permissions.ts`) does not know pinned types yet, so it may show a Super Administrator infrastructure actions that the server refuses.

## Built in forge 20b-2: Desired state, actual state and control requests

- **The `infrastructure` library app** (iteration question 12; `controlplane.AppID`): a manifest app of entity types only, defined in `features/controlplane/infra` (`app.json`, `entities/*.json`) and imported as an export document (`controlplane.Document`) then installed in the root tenant by `controlplane.SeedApp`, once (`serve --control-plane`). Its types are `infraHost`, `infraProfile`, `infraInstance`, `infraUnit`, `infraPackagePin`, `infraEnrollment` and `infraNatsAccount` (`controlplane.Entity*`). Hosts and instances carry **reported** fields the daemons fill: `facts`, `health` (`unknown`, `up`, `down`), `lastEvent`, and a host's `capabilities`. Its roles are *Desired state administrator* (every action, the installer's), *operator* (reads, and updates instances and units) and *viewer* (reads). Part question 1 settled with its proposal: desired state is records, so ops, activity, undo and live queries are the records' own.
- **The control account's state** (`controlplane.Control{NC, JS}`, `Ensure`): KV `ctl_desired` (each target's resolved desired state, keyed `host.<id>`/`inst.<id>`, `controlplane.Target`), KV `ctl_facts` (`PutFacts`, `Facts`), KV `ctl_health` with a TTL (`Beat`, `Health`; `controlplane.HealthTTL`, 30 s) and the stream `CTL` (`ctl.evt.<host|inst>.<id>.<event>`; `Report` publishes an `Event` once per request, kind and progress number by `Nats-Msg-Id`).
- **Control requests**: `ctl.<host|inst>.<id>.<verb>` request/reply (`Target.RequestSubject`, `Control.Send`; `Request{id, verb, args, actor, request}`, answered at once with `Reply{accepted}`, the outcome on `CTL` as `accepted`, `progress`, `done` or `failed`; no daemon is `ErrNoDaemon`). People change desired state with record commands on the app's records, so the operation log, activity and undo come from records; the actor rides on the record's events.
- **Followers** (`controlplane.Start`, every process, idempotent): `controlplane.desired` (a follower on the root tenant's `rec` area) resolves every host (with its instances) and every instance (with its profile, units and the package pins on it or its profile, reported fields left out) into `ctl_desired`, writing only what changed, removing targets whose record is gone, and **nudging** each changed target's daemon with a `reconcile` request; `ctl_actual` (a durable consumer on `CTL` shared by every process) folds events into `lastEvent`; a watch on `ctl_facts` copies facts into `facts`; and a sweep (2 s) marks a record `up` while its heartbeat is fresh and `down` once it is not. Reported fields change by `record.update` as the root tenant's service principal and never nudge.
- **serve --control-plane** seeds the app and starts the followers on the control account (`natsauth.AccountConn(opts, keys, "CTL", name)` with `--nats-keys`, else serve's own connection). `natsd.Options.CredsData` takes a creds file's text in place of a path.
- **The fake daemon** (`controlplanetest.FakeDaemon{C, Target, Fail}`): answers a target's requests (accepted at once, then `accepted` and `done` or `failed` on `CTL`), `SetFacts`, `Beat(every)`, `StopBeating`, `Requests`.
- **Tests** (`controlplane`): `TestDesiredAndActualState` (records reach `ctl_desired` resolved; a change nudges the fake daemon, whose outcome reaches `lastEvent`; facts reach `facts` and nudge nobody; heartbeats make the instance `up`, then `down` once they stop; a request reported ten times is one `done`; deleting the instance removes its desired state; seeding twice is once) and `TestTenantOneReadsNothing` (a tenant 1 Owner reads none of the root tenant's records).

## Built in forge 20c-1: The daemon core and enrollment

- **`controlplane/ctl`** is what the daemons and the control plane share, split out of `controlplane` so `axiomd` imports neither apps nor records: `ctl.Control` (20b-2's buckets, stream, requests and `Target`, renamed from `controlplane.Control`), and enrollment.
- **`axiomd`** (`backend/cmd/axiomd`, built without CGO by `scripts/build.sh -o out/axiomd`, version from `git describe`): `axiomd enroll --token --url [--enroll-creds --ca --mode --config --state]`, `axiomd host|agent [--config]` and `axiomd version`. Configuration is `/etc/axiomd/axiomd.json` (`daemon.Config{mode, target, natsUrls, ca, creds, state}`), the creds `/var/lib/axiomd/creds` (0600). Host and agent mode only report facts and beat for now: what they do to a machine comes with 20c-2 (LXD) and 20d-1 (packages).
- **Enrollment**: `Control.MintToken(ctx, target, ttl)` makes a random one-time token and keeps only its SHA-256 in KV `ctl_enroll` with its target and expiry; `cli controlplane enroll --target host.<id> [--keys --nats-url --ttl]` prints one. `axiomd enroll` makes its user key on the machine, connects as the shared **enroll user** (`<keys>/enroll.creds`, written by `cli nats init`; it may publish only `ctl.enroll`) and sends the token with its public key; `ctl.ServeEnroll` (queue group `ctl.enroll`, run by `serve --control-plane` with `--nats-keys`) marks the token spent by an expected-revision update and answers with a user JWT signed by the control account for that key, so the seed never leaves the machine. A spent, expired or unknown token is refused.
- **A daemon's permissions** (`ctl.DaemonPermissions(target)`): subscribe to its own `ctl.<kind>.<id>.>`, publish its own `ctl.evt.<kind>.<id>.>`, read its own `ctl_desired` key (direct get), write its own `ctl_facts` and `ctl_health` keys; nothing of another daemon's or of a tenant's.
- **The daemon core** (`controlplane/daemon`, `Daemon{Config, Reconcile, Facts, Handlers, Period, Beat}`): `Run` serves its requests (answered `accepted` at once, then `accepted`, `progress` and `done`/`failed` on `CTL`), runs `Reconcile` with its desired state on start, on a `reconcile` request and on a jittered period (5 min), and beats and reports facts (`HostFacts` plus its version, on change). A request is kept in `<state>/pending/` until done and run again after a restart; the last 200 finished ids (`done.json`) make a repeated request one `done`.
- **Tests** (`controlplane/daemon`): `TestEnrollOnce` (a token works once; spent, expired and unknown tokens are refused), `TestDaemonCredsAreScoped` (the creds read and write only the daemon's own keys and subjects), `TestReconcileAndRequests` (a desired-state change made while the daemon is stopped is applied when it returns; a request interrupted by a stop finishes after the restart; ten identical requests are one `done`).
- Part question 1 (self-update) settled with its proposal, built with packages in 20f: `axiomd` updates through its own package and the old binary runs until the new one reports healthy.
- Not built: revoking a daemon's user when its record is removed (with 20e's rendered accounts); minting a token from the browser or the infrastructure records (`infra.enroll`, with the Infrastructure pages of 20g-1) and `forge ctl enroll|requests|facts` (20g-2).
