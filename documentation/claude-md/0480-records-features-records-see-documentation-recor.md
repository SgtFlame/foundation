`records` (`features/records`, see `documentation/Records.md` › *Built in slice 16* to *Built in slice 24*) is applications' data model, built as Forge's iteration 3 in parts. An entity type (`records.EntityType`: `fields` by id, `titleField`, `indexes` and `access` declared only, `owner` `app:<appId>` or `tenant`) is an aggregate on the `def` stream (target type `entity`), changed only by `entity.*` commands (`records/entities`: `create`, `import` (the whole draft, fields keeping their ids), `setInfo`, `addField`, `updateField` as a merge, `removeField` (hides it, values kept), `restoreField`, `addIndex`, `removeIndex`, `setAccess`; `records.write`) and read through the `entity.describe {id, published?}` and `entity.list {owner?}` queries (`records.read`). Field ids are made from names when left out, never change and never start with `_`, so records keep values by id and a rename touches nothing; a field's type can change (not to or from a computed type), and publishing the change converts the records' values; `entity.delete`/`entity.restore` hide and bring back a type at once, its records kept. Every command applies its events to a copy and runs `records.Check` on the whole definition, rejecting with problems at paths like `entity.fields.<id>.relation.entity`; relations may point to `user`, the tenant's users. `entity.publish {rev}` (`records.publish`) commits a version: the `records.entityPublished` projection keeps the last, and the versions follower (`entities.Follow`) copies each into `records_entity_versions` in the tenant database, which `entityservice` serves (`GET /records/entities`, `POST /records/entities/get|versions`). The field type catalog is `records.FieldTypes`; `records.CheckValue` checks and normalizes a value for its field (decimals as strings with their scale, enums as option ids, `dateTime` in UTC) and `records.Convert` converts one to a new type. **Records** (slice 17, `records/data`): a record is an aggregate on the `rec` stream at `evt.<tenant>.rec.<entityId>.<recordId>.<event>`, changed only by `record.create {entity, values}` (no target: the bus makes a TSID; the browser sends `newRecordId()`), `record.update {entity, set, expect?}` (only changed fields, with the replaced values), `record.delete`, `record.addTo`/`removeFrom {entity, field, items}` (actions `record.create|update|delete` on the entity type's path), checked against the last **published** version, and folded by the one `records.record` projector into `PRJ_<tenant>_records_record`, keyed `<entityId>.<recordId>`, the record's own data under `_id`, `_seq` (what `expect` names; stale is `record_changed`), `_createdAt`, `_updatedAt`, `_createdBy`, `_updatedBy` and `_problems`. `records.get {entity, id}` and `records.list {entity, where?}` (a scan up to the `records` section's `scanLimit`, `record.read`) read it. The converter (`recordsdata.Follow`, started by `entities.Deps.OnPublish` and by record reads) sends the internal `record.convert` for values a published type change leaves invalid, clearing those it cannot convert with a `_problems` entry. `recordservice` (`POST /records/records/get|list|find|import`; `Create`/`Update`/`Delete` for Go only) and the `records.query`/`records.import` tools sit over them. **Indexes** (slice 18, `records/data/Index.go`): the `records.record` projector's `Keep` writes a record's entries for each index of its type's published version in the same fold, into the side bucket `PRJ_<tenant>_records_index` (`<entityId>.<indexId>.<token>….<EntryID(recordId)>`, tokens from `records.SortTokens`, order-preserving base32hex; a list-like field once per item); each index a query uses is an in-memory B-tree over its keys, loaded on first use and kept current by a watch; the indexer follower rebuilds the indexes a publication changes (`Publication.IndexChanges`) with `Rekeep`. `records.Check` refuses indexes over fields without an order (`records.Sortable`/`Indexable`). **Queries** (`records/data/Find.go`): `data.Find(args, deps, data.Query{entity, where, filter, sort, limit, cursor, fields})` walks an index in the sort's order, looks up an index's matches and sorts them, or scans up to `scanLimit`, and says which (`Plan{index, ordered, scan, read, complete}`); every record read is checked against the filter, and scans sort by the same tokens, so an index and a scan agree. `records.list` takes its snapshot from it (`where`, `filter`) and follows `Updates`; one-time sorted pages are `recordservice.Find`. **Live queries** (slice 19, `records/data/Live.go`): `records.find` takes a `Query` and keeps its page `{records, next, plan}` current without running again, sending `insert`/`update`/`move`/`remove` on the `records` list and `next` as a key; an ordered window holds its rows and up to 256 matches past it and reads the index again only when those run out, and any other plan holds every match after the cursor; a snapshot's position is the projector's (`Projections.Folded`), and a `reached` change reports progress when an event shows nothing. Test a live query against a fresh `Find` (`live_test.go`). Test the planner against an unindexed twin type (`index_test.go`); `BenchmarkQueries` loads 100 000 records. **Expansions and aggregates** (slice 20, `Expand.go`, `Aggregate.go`, `Rerun.go`): `Query.Expand` puts related records under `_expanded.<field>` (a relation to `user` reads identity through `Deps.Users`, wired in `serve.go`), and `records.aggregate` (`data.Summarize`, `recordservice.Aggregate`, `POST /records/records/aggregate`) gives `{groups: [{key, values}]}`; both run again, debounced by the `records` section's `debounceMs`, and send only the differences (`rerun`, `diff`). Use `rerun` for any record query that reads more than one record per row. **Row rules** (slice 21, `records/Rules.go`): `EntityType.Access` holds `expr-lang/expr` rules over `record` and `principal {user, tenant, kind}` (user ids as text), checked by `records.Check` and run with `records.Allows` (service principals skip them); the read rule is part of `planned.match`, so every query, expansion and aggregate applies it, and record commands refuse a hidden record as missing and a refused action with `row_rule`. Every record query is wrapped in `republished`, which restarts it when a type it reads gets a new published version. A new record query must apply the read rule the same way. Since slice 33 the rule is per principal: `EntityType.RuleFor(ctx, p, action)` adds the `or` of the principal's app roles' rules (`authz.RowRules`); always call `RuleFor`, never `Rule`. `records.Resource` puts an installed manifest app's own types at `tenant:<id>/app:<appId>/entity:<id>` (`records.SetPlacement`). Test rules with principals other than `LocalPrincipal`, which is a user (`rules_test.go`). **Record nodes** (slice 23, `records/nodes`): in `command` graphs, *Create record*, *Update record*, *Delete record*, *Add to* and *Remove from* decide through `data.Write` exactly as `record.*` does (authz, args, values, rules), reading their record with the command's `Decision.Read` (`livenodes.CommandHost.Decision`), so a graph's writes commit as one batch and a refusal commits nothing; a command graph that writes records has `area: rec`. *Get record*, *Query* and *Aggregate* read in every kind and apply the read rule; in a `data.query` graph they note `livenodes.Read{Pattern: true}` on `<entity>.*`, and the graph runs again, debounced, when one changes. Elsewhere a write is *Send command* with `record.*`. *Current user* (`live.currentUser`) gives the user id as text. **Richer fields** (slice 24): `markdown` (slice 53) is a Markdown string, edited together in `doc.markdown` and saved whole by `record.update`; `richText` is a ProseMirror doc, checked by shape (`records.PlainText` is its text), saved whole by `record.setRichText`; a `file` field holds `{id, name, size, contentType}` of an upload in the tenant's object store bucket `FILES_<tenant>` (`records/files`; `POST /records/files/upload`, served by `GET /records/files/<entity>/<record>/<field>/<file>` only to the record's readers, unsafe types as downloads), and a record command takes only a file its sender uploaded (`Deps.Files`); `volumeFile` holds `{volumeId, path}`. **Computed values are written by events**: the decision computes formulas (expr over the fields above, type checked by `records.Check`), rollups, autoNumber (the counter `_counter.<entityId>`, its `counted` event in the create's batch; `record.create` names it in `live.Command.Holds`) and createdAt/updatedAt/createdBy (`Change.Meta`) into the record's last event (`Change.Computed`); `entity.publish` resolves their value types (`Field.Returns`, `records.Resolve`, read through `records.ValueField`); the internal `record.recompute` (event `recomputed`, leaving `_updatedAt`) is sent by the converter's follower for `Publication.ComputedChanges` and by the `records.rollups` follower when related records change. Never let a command set a computed field. **Search**: fields marked `searchable` are kept in a LanceDB table per tenant by `records/search` (`Deps.Search`, a `data.Searcher`; followers `records.search` and `records.searchDefs`), searched by the live `records.search` query (`rerunOn` the index's changes; `filter` with `entity`, slice 56), `recordservice.Search`, the *Search records* node, the `records.search` tool, and the optional `records` retrieval source; at `lexicalSemantic` ≤ 0 only keyword matches are found. *Upload file* (`server.action`, `ui.handler`) and *File URL* are the file nodes. **Large tables** (slice 52, Forge 7k, `records/data/Tables.go`, `TableQuery.go`): `entity.setStorage {storage: {projection: "sql"}}` (`EntityType.SQL()`) also keeps a type's records in a tenant database table (`rec_<tenant>_<tsid>`, state in `records_tables`), written from the `rec` stream by `Deps.Tables` (`data.NewTables(gdb, projections)` in `serve.go`), migrated by `AutoMigrate` on a model built from the fields or rebuilt by replaying the stream; a row holds the record's JSON and per field its compact JSON value, sort token and summable number, list items in child tables. `planned.read` and aggregates route such types to it: filters, the read rule (`ruleSQL`), sorts and keyset cursors in SQL by the same tokens as the KV indexes, **every row checked again with `planned.match`**, so a clause need only keep a superset (`clause.exact` says when aggregates may run in SQL); a read waits until the table holds the type's events committed before it. `records.find` over one runs again (`rerunFind`). Test a change to it against a KV twin (`tables_test.go`). Full-text search stays on LanceDB (`data.Searcher`).
