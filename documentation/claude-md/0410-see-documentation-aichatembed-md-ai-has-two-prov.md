See `documentation/AIChatEmbed.md`. `ai` has two provider-neutral services, `embedservice` (`/ai/embed`) and `chatservice` (`/ai/chat`, with streaming as the `ai.chat.stream` live call), each taking a `Provider` through `impl.WithProvider`. Providers live in `features/ai/providers/<name>/` and return `providers.Error` so failures carry a status; `gemini` is the only one. Its key is chosen per call (`gemini.WithKeyFor`): the `ai.providers` setting as the call's principal (`features.CallFrom`) sees it, so a user's or tenant's own key is used for their calls, and calls with no principal (indexing) use the default tenant's; `--gemini-api-key` or `$GEMINI_API_KEY` wins over every stored key, and without any key AI calls fail with 503 and the server still runs. The model catalog with pricing is `ai.models` and the chat levels (Fast ⚡ flash-lite, Standard 💡 flash, the default, Deep 🧪 pro) are `ai.chat.levels`. `CompleteArgs.ModelRef` (an `ai.models` id) and `ThinkingBudget` (forge 15b) win over the level's, as `Temperature` and `MaxTokens` do; `CompleteArgs.Level` (`level` in the REST requests) makes `chatservice` read the level and the catalog through `config.Read` and fill the model, temperature, max output tokens and thinking budget the caller left unset, and set `Meta.Level` (Gemini 3 models refuse a budget of 0, so the provider sends it as their lowest `thinkingLevel`); the `chat` section's `debug` switch sets `Meta.Debug` on a round's calls, and `chatservice` and the provider then log each call's settings, request shape and the provider's full error at info/warn, never prompts or replies; without a level the provider's default model (`--chat-model`) is used. `chatservice.Usage` counts input (including cached), cached, output and thinking tokens separately. **Tool calling**: `CompleteArgs.Tools` (`ToolSpec{Name, Description, Parameters}`) and `ToolChoice` (`""`, `none`, `required`); the response's `Message.ToolCalls` (`{ID, Name, Args, Signature}`, the signature being Gemini's thought signature, sent back with the call); results go back as a `RoleTool` message with `Results`. Calls are not streamed: they come whole in the response. `index` (`indexservice`, `/index`) keeps volume markdown chunked (by heading, at most 4096 bytes, 512 overlapping), embedded and searchable in LanceDB (`index/store/lancestore`, `<data-dir>/lancedb`): `Find` fuses vector and BM25 rankings by weighted Reciprocal Rank Fusion. Each indexed file has a dotted sidecar `.<name>.md.index.json` (`indexservice.Meta`) with each chunk's hash, offsets, lines and head/tail anchors; unchanged chunks keep their embeddings. `conversation` (`features/conversation`, see `documentation/ChatCompletion.md` › *Built in slice 4*) runs AgentOS › Chat: `Conversation` and `Round` tables (tenanted and owned; queries always filter on the owner), and `conversationservice` under `/conversation` (`POST list|rounds`, `GET context-providers`; sending is the `conversation.send` live call). `Send` stores the round first (status 0, so usage `Meta` carries its `RoundID`) and runs the round's **mode graph** (slice 44, `documentation/ChatCompletion.md` › *Built in slice 44*; forge 06i): the mode is `SendArgs.Mode`, else the conversation's (`Conversation.Mode`), else the `chat.modes` default; `chat.modes` is built from the `chat.mode` contributions (`conversation.Modes`: Chronicle's *Personal*, the default; Forge's *Builder*, focused on Forge editors). The engine (`conversationimpl.WithEngine`) runs the mode's graph from `On user message` with the round as its host (`conversation.Host`: `Turn`, `Settings`, `Gather`, `AddContext`, `ServerTools`/`ClientTools`, `Reply`, `Say`, `SetTitle`, `Followed`), on a context the browser cannot cancel and a two-hour wall; the graph's chat nodes (`conversation/nodes`: *Context settings*, *Gather context*, *Add context*, *Messages*, *Add message*, *Stream reply*, *Say*, *Set title*, *Emit followed*) gather the context, build the prompt and tools with Go templates (`cognition/tmpl`), stream the reply (the tool loop with the gate, client tools and citations; it completes the round with every step's tokens and cost summed: 200, 499 when stopped, or the failure's status) and follow it up. A graph that ends without replying completes the round with what it said, else as failed (500). **Model nodes carry their own settings** (forge 15b, `ChatCompletion.md` › *Changed in forge 15b*): *Ask model*, *Agent*, *Stream reply* and *Run mode* take `model`, `temperature`, `maxOutputTokens`, `thinkingBudget` (`toolsnodes.ModelSettings`: config field and pin; the level fills the rest), *Ask model* `jsonSchema` (`value`), the Agent node and *Run mode* a Retrieval group `rag`; put such settings on the node that calls the model, never on a record. ***Run mode*** (`chat.runMode`, `conversationnodes.ContributeRunMode`) runs a chat mode's graph inside an agent, function, action or mode graph on `conversation.CallHost`, a headless host that stores nothing; `conversation.Headless(x.Host)` tells a node it runs there (Chronicle's *Update memory* then does nothing). The prompt builder is `conversation.Prompt`. **Never hard-code chat behaviour in Go**: prompts, tools, titles and follow-ups belong in mode graphs, which are editable built-ins (`cognition.BuiltIn.Editable`); give a new mode a `chat.mode` contribution and a graph. The call's events are `started`, `sources`, `delta`, `tool` (a `ToolCall` each time its status changes; `awaiting` and `client` wait for `answer`), `retry`, `done`, `title` (from *Set title*) and `followed` (from *Emit followed*); a message refused before its round exists gets a plain JSON error. Rounds copy their tokens and cost, priced like the usage record; the round keeps its `Mode`. `GET /conversation/modes` lists the modes with their graphs' settings (the mode kind's spec), which the composer's mode select and ⚙ use. A `ContextItem` with a `Segment` is citable: `Send` puts `Pinned` segments first in their provider's order, then the rest by score, keeps a segment found twice once (pinned), numbers them `[1]…[n]` in the prompt in the order they fit, stores them as `retrieval.RoundSegment`s and sends them as a `sources` event before the first `delta` (and again when a tool's result adds segments, numbered after them; one already cited keeps its number); `rounds` also returns each round's `toolCalls`; `rounds` returns each round's `segments` and `feedback`, `POST /conversation/feedback {roundId, feedback}` sets the verdict (`up`, `down`, `ignore` or `""`; 🚫 rounds leave the history), `POST /conversation/mode {conversationId, mode}` stores a conversation's mode when it is switched (forge 15e: the menu and `/mode`, whose matcher is `components/chat/modeMatch.ts`), and `list` takes `ids`. **The pre-mode** (forge 15f, `ChatCompletion.md` › *Changed in forge 15f*) runs the `chat` section's `preMode.graph` (kind `chat.premode`, built-in `chatPreMode`) after `started` and before the mode graph, within `budgetMs`, among the modes the browser sends as `offered` (by each mode's `purpose`): it stays, switches (event `mode`, Undo resends with `undoes`) or asks on a server-issued `chat.askChoice`; skipped with `modeChosen`. A mode needs a short, distinct `purpose`. **Made modes** (forge 15h, `ChatCompletion.md` › *Changed in forge 15h*): `features/conversation/made` keeps the modes people make as records (`chat.mode.add|update|share|delete` ops, projection and live query `chat.modes.made`) beside a published graph copied from `chatModeTemplate`, both made by the `chat.mode.create` tool in one request; read the chat modes only through `conversationsettings.ReadModes`, which adds them after the `chat.modes` settings. `GatherArgs.ContextWindow` is the round's model's window.
