**Live core** (`features/live`): a `live.Command` (`Area`, `TargetType` or `TypeOf(args)` for a command serving many types, `NewTarget` to make an id when none is sent (returned in the ack's `target`) or `NewTargetFor(args, cmdArgs)` to make it from the arguments (slice 25: a prefab's from its name), `Internal` for server-only commands without a tool, `Projection`, `Action`, `Args` schema, `Events`, `Decide(Decision) → ([]NewEvent, []Problem)`; a first problem's `Code` replaces the `command_rejected` error code) is decided by `live/bus` (`bus.Execute`): authz, `tools.CheckArgs`, the target's projected state (waiting for this process's last commit to be projected), then events published on `evt.<tenant>.<area>.<type>.<id>.<event>` with the expected last subject sequence (decided again on a conflict, three tries, then 409 `conflict`) and the command id as `Nats-Msg-Id` (duplicates dropped for 10 minutes). Several events commit as one **atomic batch** (slice 22, `documentation/Live.md` › *Built in slice 22*): an event may name another target in the command's area (`NewEvent.Target`), read first with `Decision.Read(projection, target)` so its expected sequence is checked too; `project.PublishBatch` speaks JetStream's batch headers (nats.go has no API), a retry after a conflict locks every target in key order, events carry `Event.Batch {index, count}`, and projectors write a batch's keys in one atomic batch on their bucket, so no read sees half of one. A command may name other targets it always changes in `Holds` (a counter), locked before it is decided; a batch JetStream refuses as one too many in flight (`project.IsBusy`) is sent again (slice 24). Streams are per tenant and area (`EVT_<tenant>_def|rec|app_<appId>`, kept forever, made on first use by `live/project`). A `live.Projector` (`Area`, `Types`, `Fold(live.Fold) → value`) keeps `PRJ_<tenant>_<id>` current as a durable consumer, values stored as `live.Projected{Stream, Seq, Value}`; a `live.Query` (`Params`, `Action`, `Run(live.Feed)`) sends `Snapshot` then `Change(live.Delta{replace|upsert|remove})`, list changes (`Delta.List` with `insert|update|move|remove` at `Index`/`From`) or `live.Reached` (position only; `live.Apply` applies a delta in Go, never changing the data it is given, since a UI session's props share it; `applyDelta` in the browser), mostly through `live.ValueOf` and `live.ListOf` over the `live.Store` (`project.Projections`). Positions are per stream (`live.Position`). **Every definition command is an op of the operation log** (slice 38, `documentation/Apps.md` › *Built in slice 38*): on the `def` area (`Command.Logged()`) the bus gives `Decide` a `Decision.Op`, and `Decide` must call `d.Undo(app, ops…)` with the ops that undo it, read from the state it decided against, or `d.NoUndo(app, why)`; the op rides on the commit's first event (`Event.Op`). Commands carry `request` (defaulting to the command id), `app` (the app the request was made for) and `actor` (`chat`) on `bus.Request` and the command frame; `Projector.KeyOf` keys a projection other than by target. `Projections.Follow(ctx, tenant, area, name, subjects, fn)` runs an idempotent side effect per event in order (durable consumer `fol_<name>`, retried on error, in progress while it runs), for work outside the projections such as copying into SQLite. A projector's `Keep` keeps keys outside its bucket (a `Projections.Side` bucket) in step with each value in the same fold, before the value is written; they are stored as `Projected.Kept`. Folds write with the revision they read, and `Rekeep` reruns a Keep for one key. `Updates` watches changes without the current keys, and `Settle` waits until a projector has folded its stream. Presence is `live/presence` (`presence_<tenant>`, 30 s) and the `live.presence` query; an entry's `actor` (`presence.SetAs`, slice 43) is someone working for the user (`builder`, a chat round, connection `builder-<round>`), shown by `PresenceAvatars` as its own avatar and named with `presentName(u)`. A `live.Call` streams events for a request (chat); a `live.Extension` owns frame types on every connection (`ui.*`, `collab.*`). `liveservice.Serve` runs a connection (`GET /api/v1/live`, `coder/websocket`): JSON frames by `type`, binary frames as a 4-byte channel and a payload; commands per connection in order. Tests use `natsd.StartTest(t)`.
