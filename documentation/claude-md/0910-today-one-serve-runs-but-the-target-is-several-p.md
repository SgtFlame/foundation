Today one `serve` runs, but the target is several processes per tenant on several machines sharing one JetStream (the user's direction, 2026-11-11; the NATS cluster, authorization between processes and client/server stubs are not built yet; they are designed in forge plans `020-ControlPlane.md`, `021-ProxyServerServices.md` (proxy and server implementations of every service, data services as the only owners of storage, `serve --services`) and `022-InfrastructureAsCode.md`). Build background work so it holds there: shared state in JetStream (streams, KV, durable consumers shared by name, message schedules), never in process memory; every side effect idempotent by an id (command ids, `Nats-Msg-Id`, job ids); races settled by expected-sequence commits and acks, not Go mutexes; no leader and no timer that must fire once in one process; per-process caches only as caches of JetStream state, and work that a missing precondition blocks (roles a follower syncs elsewhere) retried rather than dropped. The jobs feature is built this way. A follower that writes the local tenant database is named after the database (`records_db_instance`, as the large tables' `records.sql.<instance>.<entity>` are, slice 52), so each SQLite file gets every event. Known single-process assumptions to fix before splitting: followers that copy into the tenant SQLite database (`apps_installs`, `records_entity_versions`, `ui_prefabs`, `apps_apps`, the converter) use one shared durable consumer, so with several processes each copy lands in one process's SQLite; Cognition traces and usage records are in the local tenant database (`jobs.trace` reads the trace where the run ran); the bus's per-target locks are per process (correctness holds by expected sequences, but conflicts rise); conversations' waiting tool calls and UI sessions' handlers live in the process holding the socket; and the first read of a projection no one has used yet creates its bucket and may read it empty (seen with `cognition.published` on a fresh tenant's first `app.publish`).
